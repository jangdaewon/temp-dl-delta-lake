# 동기

본 설계 문서는 Delta를 위한 새롭고 유연하며 점진적인 클러스터링
메커니즘인 Liquid 클러스터링을 제안합니다. 사용자는 더 이상 OPTIMIZE
ZORDER BY가 요구하는 것처럼 클러스터링 열을 지정할 필요가 없습니다. 대신
클러스터링 열은 테이블 생성 시 지정되며 테이블 메타데이터에 저장됩니다.
Liquid는 또한 사용자가 워크로드에 적응하기 위해 클러스터링 열을 변경할
수 있도록 허용합니다. 클러스터링 컬럼 변경 후 기존 데이터는
재클러스터링되지 않으며, 새로 인제스트된 데이터만 새로운 클러스터링
컬럼으로 클러스터링됩니다.

파티셔닝/클러스터링은 불필요한 데이터 처리를 줄이기 위해 데이터 세트를
관리하는 일반적인 기법입니다. Hive 스타일 파티셔닝과 ZORDER 클러스터링은
Delta의 기존 솔루션이지만, 둘 다 한계가 있습니다.

## Hive 스타일 파티셔닝

Hive 스타일 파티셔닝은 각 파일이 정확히 하나의 고유한 파티션 열 값
조합을 포함하도록 데이터를 클러스터링합니다. Hive 스타일 파티셔닝은
올바르게 튜닝되면 잘 작동하지만 다음과 같은 한계가 있습니다:

- 파티션 값은 파일의 물리적 경계이므로, 고카드널리티 열을 사용한 Hive
  스타일 파티셔닝은 결합할 수 없는 수많은 작은 파일을 생성하여 스캔
  성능이 저하됩니다.

- Spark/Delta에서는 테이블이 파티셔닝된 후에는 파티션 전략을 변경할 수
  없으므로, 쿼리 패턴 변경 등 새로운 사용 사례에 적응할 수 없습니다.

## ZORDER 클러스터링

[ZORDER는 Delta에서 사용되는 다차원 클러스터링 기법입니다.]{.mark}
OPTIMIZE ZORDER BY [명령어는 ZORDER 클러스터링을 적용하여]{.mark} ZORDER
BY [열을 조건절에 사용하는 쿼리의 성능을 향상시킵니다. 그러나 다음과
같은 한계가 있습니다:]{.mark}

- [OPTIMIZE ZORDER BY는 테이블의 모든 데이터를 재작성하는 작업으로, 높은
  쓰기 증폭을 초래합니다. 또한 실행 실패 시 부분 결과가 저장되지
  않습니다.]{.mark}

- [ZORDER BY 열은 지속되지 않으며 사용자는 이전 ZORDER BY 열을 기억해야
  하므로 사용자 오류가 자주 발생합니다.]{.mark}

# 용어

- **액체 클러스터링**: [증분]{.underline} 클러스터링을 지원하기 위해
  힐베르트 곡선과 ZCube를 활용하는 클러스터링 기법입니다.

- **쓰기 증폭**: 동일한 행을 여러 번 재기록하는 것을 의미합니다.

# 요구 사항

## 기능적 요구 사항

**필수**:

- 사용자 인터페이스

  - 사용자는 Liquid 테이블 생성 시 클러스터링 열을 임의의 순서로 정의할
    수 있습니다.

  - 사용자는 [ALTER TABLE CLUSTER BY를]{.mark} 통해 기존 Liquid 테이블의
    클러스터링 열을 변경하거나 제거할 수 있습니다.

  - 기본적으로 최대 4개의 클러스터링 열을 지정할 수 있습니다.

  - 의 열 매핑 이 활성화된 경우, 사용자는 기존 Liquid 테이블의
    클러스터링 열 이름을 변경할 수 있습니다.

  <!-- -->

  - 사용자는 [OPTIMIZE]{.mark} 명령어를 통해 리퀴드 클러스터링을
    수동으로 호출할 수 있습니다.

  <!-- -->

  - 클러스터링 열은 [DESCRIBE DETAIL]{.mark} 명령을 통해 사용자에게
    노출됩니다.

  - 사용자는 [CREATE TABLE LIKE를]{.mark} 사용하여 Liquid 테이블을
    생성할 수 있습니다.

- 클러스터링

  - Liquid 클러스터링은 수집된 데이터를 증분 방식으로 클러스터링해야
    합니다.

  - Liquid 클러스터링은 현재 클러스터링 열과 함께 적용되어야 합니다.

  - Liquid 클러스터링은 적절한 파일 크기를 생성해야 하며, OPTIMIZE에
    설정된 대상 파일 크기를 준수해야 합니다.

  - 클러스터링 열을 변경한 후에는, Liquid 클러스터링은 변경 전의 기존
    데이터가 아닌 새로 수집된 데이터에만 새로운 클러스터링 열을 적용해야
    합니다.

- 기타

  - Liquid 클러스터링이 적용된 테이블을 인식하지 못하는 구형 델타 라이터
    또는 외부 라이터가 Liquid 클러스터링이 적용된 테이블에 [OPTIMIZE
    ZORDER BY를]{.mark} 실행하지 못하도록 방지해야 합니다.

# 사용자 표면

액체 클러스터링은 다음과 같은 새로운 SQL 구문을 도입합니다.

+---------------+---------------------------------------------------+
| SQL 구문      | 설명                                              |
+---------------+---------------------------------------------------+
| CREATE TABLE  | CLUSTER BY로 지정된 열을 Liquid 클러스터링 열로   |
| \<테이블\>    | 사용하는 델타 테이블을 생성합니다.                |
|               |                                                   |
| USING delta   |                                                   |
|               |                                                   |
| CLUSTER BY    |                                                   |
| (\<col1\>,    |                                                   |
| \<col2\>,     |                                                   |
| ...)          |                                                   |
+---------------+---------------------------------------------------+
| ALTER TABLE   | Liquid 클러스터링 열을 변경합니다. 변경 후 수집된 |
| \<테이블\>    | 데이터와 아직 클러스터링되지 않은 데이터는 새로운 |
|               | 클러스터링 열로 클러스터링됩니다.                 |
| CLUSTER BY    |                                                   |
| (\<col1\>,    |                                                   |
| \<col2\>,     |                                                   |
| ...)          |                                                   |
+---------------+---------------------------------------------------+
| ALTER TABLE   | Liquid 클러스터링 열을 제거합니다. 향후 수집되는  |
| \<테이블\>    | 데이터에 대해서는 클러스터링이 수행되지 않습니다. |
|               |                                                   |
| CLUSTER BY    |                                                   |
| NONE          |                                                   |
+---------------+---------------------------------------------------+
| OPTIMIZE      | Liquid 클러스터링을 트리거합니다. 기존 OPTIMIZE   |
| \<테이블\>    | 의미론(파일 압축)과 달리, Liquid 테이블에 대한    |
|               | OPTIMIZE는 클러스터링 열이 설정되지 않은 경우     |
|               | 압축을 트리거하고, 그렇지 않은 경우 클러스터링을  |
|               | 트리거합니다.                                     |
|               |                                                   |
|               | 클러스터링된 테이블에는 OPTIMIZE ZORDER BY를      |
|               | 사용할 수 없습니다.                               |
+===============+===================================================+

Liquid 클러스터링은 다음과 같은 새로운 DeltaTable API를 도입합니다:

  -------------------------------------------------------------------------
  API 이름              설명
  --------------------- ---------------------------------------------------
  clusterBy(colNames:   CLUSTER BY로 지정된 열을 Liquid 클러스터링 열로
  String\*):            사용하는 Delta 테이블을 생성합니다.
  DeltaTableBuilder     

  -------------------------------------------------------------------------

clusterBy()가 OSS Spark(WIP)에서 사용 가능해지면 DataFrameWriter API
작업을 진행할 예정입니다.

# 제안 개요

## 힐베르트 곡선을 활용한 향상된 클러스터링

[현재 Delta는 데이터 클러스터링을 위해 Z-Order 곡선([[설계
문서]{.underline}](https://docs.google.com/document/d/1TYFxAUvhtYqQ6IHAZXjliVuitA5D1u793PMnzsH_3vs/edit))을
활용하는 OPTIMIZE ZORDER BY 명령을 지원합니다. Liquid의 다차원
클러스터링 기법으로 연속적인 프랙탈 공간 채움 곡선인]{.mark}
[[[Hilbert]{.underline}]{.mark}
[[곡선을]{.underline}]{.mark}](https://en.wikipedia.org/wiki/Hilbert_curve)
[사용하도록 제안합니다. 이는 ZORDER 대비 데이터 스킵을 크게
개선합니다.]{.mark}

[ZORDER의 작동 방식과 유사하게, 힐베르트 곡선은 다차원 데이터를 곡선에
맞추어 1차원 공간으로 매핑합니다. 이는 지역성을 매우 잘 보존하여 1차원
공간에서 가까운 점들은 다차원 공간에서도 가까워야 함을 의미합니다.
우리는 이 특성을 활용하여 효율적인 데이터 스키핑을 수행할 수 있습니다.
다음은 64개의 고유 레코드를 가진 간단한 두 열 테이블의 예시입니다. 점선
사각형 하나는 하나의 파일을 나타내며, 각 파일에는 4개의 레코드가
포함됩니다.]{.mark}

[힐베르트 곡선의 훌륭한 특성(그림 1 참조)을 기억하시나요? Z-곡선은 그
특성을 갖지 않습니다. Z-곡선의 인접 점들은 항상 거리 = 1을 가지지 않으며
곡선 내에 큰 점프가 존재합니다. 이러한 점프는 곡선의 부분 범위에서 경계
상자 크기의 비선형적(그리고 잠재적으로 엄청난) 증가로 이어집니다. 예를
들어, 길이 6인 동일한 주황색 선을 살펴보겠습니다. Z-커브의 경우, 그림
3에 표시된 바운딩 박스가 전체 공간을 덮습니다! 힐베르트 곡선의 경우, 이

사분면만 덮을 수 있기 때문입니다. 이는 Z-순서에서 잠재적으로 일부 파일의
최소/최대 범위가 전체 범위와 같을 수 있으며, 데이터 스키핑이 이러한
파일을 건너뛸 수 없음을 의미합니다.]{.mark}

## ZCube를 이용한 증분 클러스터링

현재 OPTIMIZE ZORDER BY는 마지막 실행 이후 새 파일이 추가되지 않았더라도
모든 데이터를 재작성해야 합니다. 이로 인해 대규모 테이블에서 실행 비용이
매우 높습니다. 또한 실패 시 모든 진행 상황이 손실되어 다음 실행은
처음부터 시작해야 합니다.

Liquid를 통해 증분 클러스터링 기능을 도입하여 사용자가 모든 데이터를
재작성하지 않고도 OPTIMIZE를 실행할 수 있도록 제안합니다. OPTIMIZE는
또한 배치 단위로 완료되며, 각 배치는 단일 OPTIMIZE 커밋을 생성하므로
문제가 발생해도 모든 진행 상황이 손실되지 않습니다.

증분 클러스터링은 ZCubes 개념을 중심으로 구축됩니다. **ZCube는** 동일한
OPTIMIZE 작업으로 생성된 파일 그룹입니다. 새로 생성되거나 최적화되지
않은 파일만 재작성하고자 하므로( ), AddFile의 ZCUBE_ID 태그를 사용하여
이미 최적화된 파일(특정 ZCubes에 속함)과 최적화되지 않은 파일을
구분합니다. 새로운 ZCube마다 UUID를 사용하여 고유한 ZCUBE_ID를
생성합니다.

클러스터링할 파일을 선택하는 몇 가지 전략이 있으며, 자세한 내용은
[[여기에서]{.underline}](#kix.301alpimymwh) 확인할 수 있습니다.

클러스터링 대상 파일 선택의 유연성을 제공하기 위해 두 가지 구성을
도입합니다:

- **MIN_CUBE_SIZE**: 증분 OPTIMIZE 과정에서 더 이상 새 데이터가 병합되지
  않는 ZCube 크기입니다. 기본값은 100GB입니다.

- **TARGET_CUBE_SIZE**: 생성할 ZCubes의 목표 크기입니다. 이는 엄격한
  최대값이 아닙니다. 파일들의 합산 크기가 이 값을 초과할 때까지 ZCube에
  파일을 계속 추가합니다. 이 값은 MIN_CUBE_SIZE 이상이어야 합니다.
  기본값은 150GB입니다.

*MIN_CUBE_SIZE보다* 작은 크기의 ZCubes는 **부분 ZCube라고** 부릅니다.
모든 새 파일은 OPTIMIZE 대상으로 고려되지만, 기존 부분 ZCubes도 함께
고려됩니다. 부분 ZCube가 충분한 데이터를 축적하여 *MIN_CUBE_SIZE*
임계값을 넘으면 **안정적인 ZCube로** 전환되며, 이 시점부터는 재기록
대상으로 더 이상 고려되지 않습니다.

*그림 5: ZCube 기반 증분 클러스터링*

DML 작업으로 너무 많은 파일이 삭제되면 안정적인 ZCube가 다시 부분
ZCube가 될 수 있으며, 이때 부분 ZCube의 파일은 클러스터링 대상으로
고려됩니다.

*그림 6: 삭제 후 안정적 ZCube가 부분적 상태로 전환되는 모습*

의 특수한 경우로, 사용자가 클러스터링 열을 변경할 때 기존 데이터는
그대로 유지하고, 그 시점부터 새로운 클러스터링 열 을 사용하여 새
데이터만 클러스터링하고자 합니다. 따라서 AddFile에서 클러스터링 열을
ZCUBE_ZORDER_BY 태그를 사용하여 지속화하며, 이 태그는 해당 파일이 어떤
클러스터링 열로 클러스터링되었는지 나타냅니다. 후보 파일을 선택할 때
다른 클러스터링 열 세트를 가진 파일은 필터링하여 제외합니다.

*그림 7: ZCube를 사용한 OPTIMIZE의 흐름*

위의 그림은 ZCubes를 사용한 [OPTIMIZE의]{.mark} 흐름을 보여줍니다. T o
begin, we select our candidate files, which encompass both fresh data
and any partial ZCubes with the same clustering columns as our current
clustering columns. Then we bin pack the files into multiple ZCubes and
run the clustering algorithm on each of the ZCubes. 실행 후에는 충돌
발생 시 부분 결과가 저장되도록 각 ZCube당 하나의 커밋을 생성합니다.

## 사용자 표면

사용자는 더 이상 [ZORDER BY]{.mark} 열을 지정할 필요가 없습니다. 대신,
테이블 생성 시 다음 구문을 사용하여 클러스터링 열을 지정합니다.

CREATE TABLE \<테이블\> USING delta CLUSTER BY (\<col1\>, \<col2\>,
...)

그러면 클러스터링 열이 메타데이터에 저장되며, 사용자는
[OPTIMIZE]{.mark} 명령어를 실행하기만 하면 클러스터링이 트리거됩니다.

사용자는 ALTER TABLE CLUSTER BY를 실행하여 클러스터링 열을 변경할 수도
있습니다. 두 가지 변형이 있습니다:

1.  ALTER TABLE CLUSTER BY (col1, col2): 클러스터링 열을 업데이트합니다.
    기존 클러스터링 데이터는 변경되지 않으며, 새 데이터는 새로운
    클러스터링 열을 기준으로 클러스터링됩니다.

2.  ALTER TABLE CLUSTER BY NONE: 기존 클러스터링 열을 모두 제거합니다.
    이미 클러스터링된 데이터는 변경되지 않으며, 새 데이터는
    클러스터링되지 않습니다. 대신 [OPTIMIZE가]{.mark} 새 데이터를
    압축합니다. 이는 파일 압축을 실행하는 기존 [OPTIMIZE와]{.mark}
    유사합니다.

메타데이터

액체 클러스터링은 도메인 메타데이터([[설계
문서]{.underline}](https://docs.google.com/document/d/16MHP7P78cq9g8SWhAyfgFlUe-eH0xhnMAymgBVR1fCA/edit#heading=h.c60ogungpazw))를
활용하여 클러스터링 열을 도메인 메타데이터 작업으로 저장합니다. 이는
클러스터링 테이블
기능([[PR]{.underline}](https://github.com/delta-io/delta/pull/2264))의
일부입니다:

{

\"domainMetadata\": {

\"domain\": \"delta.clustering\",

\"configuration\": \"{\\\"keys\\\":\\\"colA,colB\\\"}\"

}

}



액체 클러스터링은 변경도 지원하며, [[열
매핑이]{.underline}](https://docs.delta.io/latest/delta-column-mapping.html)
활성화된 경우 클러스터링 열의 이름 변경도 가능합니다. 단, 클러스터링 열
삭제는 허용되지 않지만, 사용자는 언제든지 \`ALTER TABLE CLUSTER BY\`를
사용하여 클러스터링 열에서 열을 이동한 후 삭제할 수 있습니다. 열 매핑을
지원하기 위해 메타데이터에 열의 물리적 이름을 저장하고, [\`DESCRIBE
DETAIL]{.mark}\`과 같은 사용자 대상 명령어를 위해 논리적 열 이름을
추출합니다.

# 프로토콜 변경

Liquid 클러스터링은 ClusteringTableFeature를 활용하므로 Delta 프로토콜에
대한 추가 변경 사항은 없습니다.

ClusteringTableFeature에 의존하기로 한 설계 결정은
[[여기에서]{.underline}](#kix.4glx7twzj97m) 확인할 수 있습니다.

# 설계 결정

## 결정 1: 이미 최적화된 파일을 다시 작성해야 할까요?

### 옵션 1: 항상 모든 파일을 다시 작성

이는 단 하나의 ZCube만 유지하고, 모든 OPTIMIZE 실행 시 기존 ZCube를
최적화되지 않은 데이터와 병합하는 것을 의미합니다. 이는 현재 구현
방식이며, 긴 OPTIMIZE 시간과 큰 쓰기 증폭을 초래합니다.

### 옵션 2: 새로 들어온 데이터만 최적화

이는 기존 ZCube와의 병합을 절대 수행하지 않음을 의미합니다. 그러나 많은
작은 ZCube는 데이터 건너뛰기 효율성에 좋지 않습니다. 각 ZCube 내에서는
데이터 건너뛰기 비율이 비슷할 수 있지만, ZCube 간 전체 순서가 없기
때문에 각 ZCube에 대해 데이터 건너뛰기를 수행해야 하며, 스캔 시간은
ZCube 수에 선형적으로 비례합니다.

### 옵션 3 (권장): 최소 큐브 크기 임계값 사용

이 접근법에서는 모든 새 파일과 함께 주어진 임계값보다 작은 기존 큐브도
병합합니다. 이는 옵션 1보다 낮은 쓰기 증폭률을 제공하면서도 옵션 2보다
적은 ZCube 수를 유지하므로, 옵션 2보다 우수한 읽기 성능을 제공합니다.

## 결정 2: Liquid 전용 테이블 기능을 도입해야 할까요?

### 옵션 1: 아니오, 하지만 ClusteringTableFeature에 의존 (권장)

ClusteringTableFeature([[PR]{.underline}](https://github.com/delta-io/delta/pull/2264))을
활용하면 구형 Delta Lake 버전 및 외부 라이터가 Liquid 테이블에 OPTIMIZE
ZORDER BY를 실행하는 것을 방지할 수 있으며, 이는 Liquid 테이블이
유지하는 클러스터링을 무효화합니다.

CLUSTERED_BY를 liquid로 설정하여 OPTIMIZE의 출력 파일에 태그를
지정함으로써 ClusteringTableFeature의 사양을 따를 것입니다.

### 옵션 2: 아니오

외부 리더/라이터가 지원해야 할 추가 테이블 기능이 없습니다. 그러나
라이터는 OPTIMIZE ZORDER BY를 실행하여 Liquid 테이블의 클러스터링을
무효화할 수 있습니다.

### 옵션 3: 예, LiquidTableFeature 도입

이 방법은 옵션 1과 동일한 이점을 제공하지만, 추가 테이블 기능을 도입하는
데 따른 추가 오버헤드가 발생합니다. ClusteringTableFeature는 바로 이러한
목적을 위해 설계되었으며, 모든 종류의 클러스터링 구현을 위한 테이블
기능으로 사용됩니다.
