# 개요
이 문서는 Delta Transaction Protocol의 사양으로, 분산 파일 시스템 또는 객체 저장소에 파일로 저장된 대용량 데이터 컬렉션에 [ACID](https://en.wikipedia.org/wiki/ACID) 속성을 제공합니다. 이 프로토콜은 다음과 같은 목표를 염두에 두고 설계되었습니다:

- **직렬화 가능한 ACID 쓰기** - 여러 Writer가 ACID 의미를 유지하면서 동시에 Delta 테이블을 수정할 수 있습니다.
- **읽기를 위한 스냅샷 격리** - Reader는 동시 쓰기가 발생하는 경우에도 Delta 테이블의 일관된 스냅샷을 읽을 수 있습니다.
- **수십억 개의 파티션 또는 파일로의 확장성** - Delta 테이블에 대한 쿼리는 단일 머신 또는 병렬로 계획될 수 있습니다.
- **자체 설명** - Delta 테이블의 모든 메타데이터는 데이터와 함께 저장됩니다. 이 설계는 데이터를 읽기 위해 별도의 메타스토어를 유지할 필요를 제거하며, 표준 파일 시스템 도구를 사용하여 정적 테이블을 복사하거나 이동할 수 있도록 합니다.
- **증분 처리 지원** - Reader는 Delta 로그를 추적하여 특정 기간 동안 추가된 데이터를 확인할 수 있으므로 효율적인 스트리밍이 가능합니다.

Delta의 트랜잭션은 다중 버전 동시성 제어(MVCC)를 사용하여 구현됩니다.
테이블이 변경될 때, Delta의 MVCC 알고리즘은 업데이트되거나 제거되는 레코드가 포함된 파일을 즉시 교체하는 대신 데이터의 여러 복사본을 유지합니다.

테이블의 Reader는 _트랜잭션 로그_를 사용하여 처리할 _데이터 파일_을 선택적으로 선택함으로써 한 번에 테이블의 일관된 _스냅샷_ 하나만 볼 수 있도록 보장합니다.

Writer는 두 단계로 테이블을 수정합니다:
먼저, 낙관적으로 새로운 데이터 파일 또는 기존 파일의 업데이트된 복사본을 작성합니다.
그런 다음 _커밋_하여 로그에 새 엔트리를 추가함으로써 테이블의 최신 _원자적 버전_을 생성합니다.
이 로그 엔트리에서 논리적으로 추가 및 제거할 데이터 파일과 테이블에 대한 다른 메타데이터의 변경 사항을 기록합니다.

테이블의 최신 버전에 더 이상 존재하지 않는 데이터 파일은 사용자가 지정한 보존 기간(기본 7일) 후 vacuum 명령으로 지연 삭제될 수 있습니다.

# Delta 테이블 사양
테이블은 연속적이고 단조 증가하는 정수를 사용하여 명명되는 단일 직렬 원자적 버전 히스토리를 가집니다.
특정 버전에서의 테이블 상태를 _스냅샷_이라고 하며 다음 속성으로 정의됩니다:
- **Delta 로그 프로토콜**은 두 가지 **프로토콜 버전**과 해당되는 경우 테이블을 올바르게 읽거나 쓰는 데 필요한 **테이블 기능**으로 구성됩니다
    - **Reader 기능**은 Reader 버전이 3인 경우에만 존재합니다
    - **Writer 기능**은 Writer 버전이 7인 경우에만 존재합니다
- 테이블의 **메타데이터** (예: 스키마, 고유 식별자, 파티션 컬럼 및 기타 구성 속성)
- 테이블에 있는 **파일 집합**과 해당 파일에 대한 메타데이터
- 최근에 삭제된 파일에 대한 **툼스톤 집합**
- 테이블에 성공적으로 커밋된 **애플리케이션별 트랜잭션 집합**

## 파일 타입
Delta 테이블은 디렉토리 내에 저장되며 다음과 같은 다양한 타입의 파일로 구성됩니다.

다음은 `mytable` 디렉토리에 저장된 커밋 로그에 4개의 엔트리가 있는 Delta 테이블의 예입니다.
```
/mytable/_delta_log/00000000000000000042.json
/mytable/_delta_log/00000000000000000042.checkpoint.parquet
/mytable/_delta_log/00000000000000000043.json
/mytable/_delta_log/00000000000000000044.json
/mytable/_delta_log/00000000000000000045.json
/mytable/_delta_log/_last_checkpoint
/mytable/_change_data/cdc-00000-924d9ac7-21a9-4121-b067-a0a6517aa8ed.c000.snappy.parquet
/mytable/part-00000-3935a07c-416b-4344-ad97-2a38342ee2fc.c000.snappy.parquet
/mytable/deletion_vector-0c6cbaaf-5e04-4c9d-8959-1088814f58ef.bin
```

이 예제는 [메타데이터 정리](#메타데이터-정리)가 이전 로그 엔트리를 제거한 후의 테이블을 나타냅니다. 버전 42의 체크포인트에는 완전한 테이블 상태가 포함되어 있으며, 버전 43-45는 후속 커밋입니다. 각 파일 타입은 아래 섹션에서 설명합니다.

### 데이터 파일
데이터 파일은 테이블의 루트 디렉토리 또는 숨겨지지 않은 하위 디렉토리(즉, 이름이 `_`로 시작하지 않는 디렉토리)에 저장될 수 있습니다.
기본적으로 참조 구현은 해당 파일의 데이터에 대한 파티션 값을 기반으로 명명된 디렉토리에 데이터 파일을 저장합니다(예: `part1=value1/part2=value2/...`).
이 디렉토리 형식은 기존 규칙을 따르기 위해서만 사용되며 프로토콜에서 요구하지 않습니다.
파일의 실제 파티션 값은 트랜잭션 로그에서 읽어야 합니다.

### 삭제 벡터 파일
삭제 벡터(DV) 파일은 데이터 파일과 함께 테이블의 루트 디렉토리에 저장됩니다. DV 파일에는 연결된 특정 데이터 파일에 대해 *무효화된*(또는 "소프트 삭제된") 행 집합을 설명하는 하나 이상의 직렬화된 DV가 포함됩니다.
파티션 값이 있는 데이터의 경우, DV 파일은 여러 파티션의 파일에 대한 DV를 포함할 수 있으므로 데이터 파일과 동일한 디렉토리 계층 구조에 보관되지 *않습니다*.
DV 파일은 [바이너리 형식](#삭제-벡터-형식)으로 DV를 저장합니다.

### 변경 데이터 파일
변경 데이터 파일은 테이블 루트의 `_change_data`라는 디렉토리에 저장되며 해당 테이블 버전의 변경 사항을 나타냅니다. 파티션 값이 있는 데이터의 경우, 변경 데이터 파일을 각 파티션의 `_change_data` 디렉토리 내에 저장하는 것이 권장됩니다(예: `_change_data/part1=value1/...`). Writer는 Delta Lake 테이블에 대한 `UPDATE`, `DELETE`, `MERGE` 작업과 같이 기본 데이터를 변경하는 작업의 결과로 이러한 변경 데이터 파일을 _선택적으로_ 생성할 수 있습니다. 작업이 기존 행을 업데이트하지 않고 새 데이터만 추가하거나 기존 데이터를 제거하는 경우, Writer는 데이터 파일만 작성하고 데이터를 변경 데이터 파일에 복제하지 않고 `add` 또는 `remove` 액션으로 커밋할 수 있습니다. 사용 가능한 경우, 변경 데이터 Reader는 기본 데이터 파일에서 변경 사항을 계산하는 대신 변경 데이터 파일을 사용해야 합니다.

데이터 컬럼 외에도 변경 데이터 파일에는 변경 이벤트 유형을 식별하는 추가 컬럼이 포함됩니다:

필드 이름 | 데이터 타입 | 설명
-|-|-
_change_type|`String`| `insert`, `update_preimage` , `update_postimage`, `delete` __(1)__

__(1)__ `preimage`는 업데이트 전의 값이고, `postimage`는 업데이트 후의 값입니다.

### Delta 로그 엔트리
Delta 파일은 `_delta_log`라는 테이블 루트의 디렉토리에 JSON으로 저장되며 체크포인트와 함께 테이블에 발생한 모든 변경 사항의 로그를 구성합니다.

Delta 파일은 테이블의 원자성 단위이며 사용 가능한 다음 버전 번호를 사용하여 명명되며 20자리로 0으로 채워집니다.

예를 들어:

```
./_delta_log/00000000000000000000.json
```
Delta 파일은 개행으로 구분된 JSON 형식을 사용하며, 모든 액션은 단일 줄 JSON 문서로 저장됩니다.
Delta 파일 `n.json`에는 테이블의 `n`번째 스냅샷을 구성하기 위해 이전 테이블 상태 `n-1.json`에 적용되어야 하는 원자적 [_액션_](#액션) 집합이 포함되어 있습니다.
액션은 테이블 상태의 한 측면을 변경합니다(예: 파일 추가 또는 제거).

### 체크포인트
체크포인트도 `_delta_log` 디렉토리에 저장되며 테이블의 모든 커밋된 버전에 대해 언제든지 생성될 수 있습니다.
성능상의 이유로 Reader는 가능한 최신의 완전한 체크포인트를 사용하는 것이 좋습니다.
시간 여행의 경우 사용되는 체크포인트는 시간 여행 버전보다 최신이어서는 안 됩니다.

체크포인트에는 [조정 규칙](#액션-조정)을 사용하여 무효한 액션이 제거된 체크포인트된 테이블 버전까지 모든 액션의 완전한 재생이 포함됩니다.
무효한 액션은 후속 액션에 의해 취소된 액션입니다(예: 추가된 파일 제거).
또한 체크포인트에는 만료될 때까지 [_제거 툼스톤_](#파일-추가-및-파일-제거)도 포함됩니다.
체크포인트를 사용하면 Reader가 스냅샷을 재구성하기 위해 특정 시점까지 로그를 읽는 비용을 단축할 수 있으며, [메타데이터 정리](#메타데이터-정리)가 만료된 JSON Delta 로그 엔트리를 삭제할 수 있습니다.

Reader는 체크포인트의 존재나 빈도에 대해 어떠한 가정도 해서는 안 됩니다. 한 가지 예외가 있습니다:
[메타데이터 정리](#메타데이터-정리)는 삭제된 [Delta 로그 엔트리](#delta-로그-엔트리)를 모두 포함하기 위해 가장 오래된 보존된 테이블 버전에 대한 체크포인트를 제공해야 합니다.
그러나 Writer는 Reader가 많은 수의 Delta 파일을 읽음으로 인한 과도한 로그 재생 비용을 지불하지 않도록 합리적으로 자주 체크포인트를 생성하는 것이 권장됩니다.

체크포인트 파일 이름은 체크포인트가 포함하는 테이블 버전을 기반으로 합니다.

Delta는 세 가지 종류의 체크포인트를 지원합니다:

1. UUID 명명 체크포인트: 다음 파일 이름을 사용하는 [V2 사양](#v2-사양)을 따릅니다: `n.checkpoint.u.{json/parquet}`, 여기서 `u`는 UUID이고 `n`은 이 체크포인트가 나타내는 스냅샷 버전입니다. 여기서 `n`은 길이 20이 되도록 0으로 채워져야 합니다. UUID 명명 V2 체크포인트는 json 또는 parquet 형식일 수 있으며 `_delta_log/_sidecars` 디렉토리에 0개 이상의 체크포인트 사이드카를 참조합니다. 체크포인트 사이드카는 고유하게 명명된 parquet 파일입니다: `{unique}.parquet` 여기서 `unique`는 UUID와 같은 고유 문자열입니다.

예를 들어:

```
00000000000000000010.checkpoint.80a083e8-7026-4e79-81be-64bd76c43a11.json
_sidecars/3a0d65cd-4056-49b8-937b-95f9e3ee90e5.parquet
_sidecars/016ae953-37a9-438e-8683-9a9a4a79a395.parquet
_sidecars/7d17ac10-5cc3-401b-bd1a-9c82dd2ea032.parquet
```

2. 테이블의 버전 `n`에 대한 [클래식 체크포인트](#클래식-체크포인트)는 `n.checkpoint.parquet`라는 파일로 구성됩니다. 여기서 `n`은 길이 20이 되도록 0으로 채워져야 합니다.
   이들은 [V1 사양](#v1-사양) 또는 [V2 사양](#v2-사양)을 따를 수 있습니다.
   예를 들어:

```
00000000000000000010.checkpoint.parquet
```

3. 버전 `n`에 대한 [다중 파트 체크포인트](#다중-파트-체크포인트)는 `p`개의 "파트" 파일(`p > 1`)로 구성되며, `p` 중 파트 `o`는 `n.checkpoint.o.p.parquet`로 명명됩니다. 여기서 `n`은 길이 20이 되도록 0으로 채워져야 하고, `o`와 `p`는 길이 10이 되도록 0으로 채워져야 합니다. 이들은 항상 [V1 체크포인트](#v1-사양)입니다.
   예를 들어:

```
00000000000000000010.checkpoint.0000000001.0000000003.parquet
00000000000000000010.checkpoint.0000000002.0000000003.parquet
00000000000000000010.checkpoint.0000000003.0000000003.parquet
```

Writer는 다음 제약 조건으로 체크포인트를 작성할 수 있습니다:
- Writer는 항상 [v1 사양](#v1-사양)을 따르는 [클래식 체크포인트](#클래식-체크포인트)를 생성할 수 있습니다.
- [v2 체크포인트](#v2-체크포인트-테이블-기능)가 활성화된 경우 Writer는 [다중 파트 체크포인트](#다중-파트-체크포인트)를 생성할 수 없습니다.
- [v2 체크포인트 테이블 기능](#v2-체크포인트-테이블-기능)이 활성화된 경우 Writer는 v2 사양 체크포인트([클래식](#클래식-체크포인트) 또는 [uuid 명명](#uuid-명명-체크포인트))를 생성할 수 있습니다.

다중 파트 체크포인트는 [더 이상 사용되지 않으며](#다중-파트-체크포인트의-문제점), Writer는 이를 생성하지 않아야 합니다. 대신 UUID 명명 [V2 사양](#v2-사양) 체크포인트를 사용하세요.

동일한 테이블 버전에 대해 여러 체크포인트가 존재할 수 있습니다. 예를 들어 두 클라이언트가 동시에 체크포인트를 생성하지만 다른 형식으로 생성하는 경우입니다.
이러한 경우 클라이언트는 사용할 체크포인트를 선택할 수 있습니다.

다중 파트 체크포인트는 원자적으로 생성될 수 없기 때문에(예: 느리거나 실패한 쓰기에 취약), Reader는 파트가 누락된 다중 파트 체크포인트를 무시해야 합니다.

특정 버전에 대한 체크포인트는 관련된 Delta 파일이 성공적으로 작성된 후에만 생성되어야 합니다.

#### 사이드카 파일

사이드카 파일에는 파일 액션이 포함됩니다. 이러한 파일은 parquet 형식이며 고유한 이름을 가져야 합니다.
그런 다음 체크포인트에 [연결](#사이드카-파일-정보)됩니다. 자세한 내용은 [V2 체크포인트 사양](#v2-사양)을 참조하세요. 현재 사이드카 파일에는 [파일 추가 및 파일 제거](#파일-추가-및-파일-제거) 엔트리만 포함될 수 있습니다. add 및 remove 파일 액션은 struct 필드로 parquet의 개별 컬럼으로 저장됩니다.

이러한 파일은 `_delta_log/_sidecars` 디렉토리에 있습니다.

### 로그 압축 파일

로그 압축 파일은 `_delta_log` 디렉토리에 있습니다. 시작 버전 `x`에서 종료 버전 `y`(`y`는 `x`보다 _커야_ 함)까지의 로그 압축 파일은 다음 이름을 갖습니다:
`<x>.<y>.compacted.json`. 여기에는 커밋 범위 `[x, y]`에 대한 집계된 액션이 포함됩니다. 커밋과 유사하게 로그 압축 파일의 각 행은 [액션](#액션)을 나타냅니다.
특정 범위의 커밋 파일은 해당 커밋의 [액션 조정](#액션-조정)을 수행하여 생성됩니다.
범위 `[x, y]`의 개별 커밋 파일을 읽는 대신 구현에서 로그 압축 파일 `<x>.<y>.compacted.json`을 읽어 스냅샷 구성 속도를 높일 수 있습니다.

예제:
`00000000000000000004.json`이 다음과 같다고 가정합니다:
```
{"commitInfo":{...}}
{"add":{"path":"f2",...}}
{"remove":{"path":"f1",...}}
```
`00000000000000000005.json`이 다음과 같다고 가정합니다:
```
{"commitInfo":{...}}
{"add":{"path":"f3",...}}
{"add":{"path":"f4",...}}
{"txn":{"appId":"3ae45b72-24e1-865a-a211-34987ae02f2a","version":4389}}
```
`00000000000000000006.json`이 다음과 같다고 가정합니다:
```
{"commitInfo":{...}}
{"remove":{"path":"f3",...}}
{"txn":{"appId":"3ae45b72-24e1-865a-a211-34987ae02f2a","version":4390}}
```

그러면 `00000000000000000004.00000000000000000006.compacted.json`은 다음 내용을 갖습니다:
```
{"add":{"path":"f2",...}}
{"add":{"path":"f4",...}}
{"remove":{"path":"f1",...}}
{"remove":{"path":"f3",...}}
{"txn":{"appId":"3ae45b72-24e1-865a-a211-34987ae02f2a","version":4390}}
```

Writer:
- 선택적으로 주어진 커밋 범위에 대한 로그 압축을 생성할 수 있습니다

Reader:
- 선택적으로 사용 가능한 경우 로그 압축을 사용할 수 있습니다
- 압축은 액션 조정 중에 해당 커밋을 대체합니다

### 마지막 체크포인트 파일
Delta 트랜잭션 로그는 종종 많은(예: 10,000개 이상) 파일을 포함합니다.
이러한 큰 디렉토리를 나열하는 것은 엄청나게 비쌀 수 있습니다.
마지막 체크포인트 파일은 로그 끝 근처의 포인터를 제공하여 테이블의 최신 스냅샷을 구성하는 비용을 줄이는 데 도움이 될 수 있습니다.

전체 디렉토리를 나열하는 대신 Reader는 `_delta_log/_last_checkpoint` 파일을 보고 최근 체크포인트를 찾을 수 있습니다.
로그에 있는 파일의 0으로 채워진 인코딩 때문에 이 최근 체크포인트의 버전 ID는 사전순으로 정렬되고 페이징된 디렉토리 목록을 지원하는 저장 시스템에서 테이블의 더 최근 버전을 구성하는 Delta 파일 또는 더 새로운 체크포인트를 열거하는 데 사용될 수 있습니다.

### 버전 체크섬 파일

Delta 트랜잭션 로그는 추가 전용 로그로 유지되어야 합니다. Delta 파일에 대한 비준수 수정 감지를 가능하게 하기 위해 Writer는 선택적으로 모든 커밋과 함께 해당 버전의 테이블 상태에 대한 중요한 정보를 포함하는 보조 파일을 내보낼 수 있습니다. 이 파일을 **버전 체크섬**이라고 하며 테이블의 무결성을 검증하는 데 사용할 수 있습니다.

### 버전 체크섬 파일 스키마

버전 체크섬 파일은 다음 속성을 가져야 합니다:
- `{version}.crc`로 명명되며 여기서 `version`은 20자리로 0으로 채워집니다(예: `00000000000000000001.crc`)
- Delta 로그 파일과 함께 `_delta_log` 디렉토리에 직접 저장됩니다
- 다음 스키마를 가진 정확히 하나의 JSON 객체를 포함합니다:

필드 이름 | 데이터 타입 | 설명 | 선택/필수
-|-|-|-
txnId | String | 이 커밋을 생성한 트랜잭션의 고유 식별자. | 선택

numFiles | Long | 액션 조정 후 이 테이블 버전의 라이브 `add` 액션 수. | 필수

##### 파일 크기 히스토그램 스키마

`FileSizeHistogram` 객체는 다양한 크기 범위에서 파일 수와 총 바이트를 추적하는 히스토그램을 나타냅니다. 다음 스키마를 갖습니다:

필드 이름 | 데이터 타입 | 설명 | 선택/필수
-|-|-|-
sortedBinBoundaries | Array[Long] | 각 요소가 bin의 시작(포함)을 나타내고 다음 요소가 bin의 끝(제외)을 나타내는 정렬된 bin 경계 배열. 첫 번째 요소는 0이어야 합니다. | 필수
fileCounts | Array[Long] | 각 bin의 파일 수. 길이가 `sortedBinBoundaries`와 일치해야 합니다. | 필수
totalBytes | Array[Long] | 각 bin의 파일 총 바이트. 길이가 `sortedBinBoundaries`와 일치해야 합니다. | 필수

이러한 배열의 각 인덱스 `i`는 `sortedBinBoundaries[i]`(포함)부터 `sortedBinBoundaries[i+1]`(제외)까지의 크기 범위에 해당합니다. 마지막 bin은 양의 무한대에서 끝납니다. 예를 들어 경계 `[0, 1024, 4096]`가 주어진 경우:
- Bin 0은 크기 [0, 1024) 바이트의 파일을 포함합니다
- Bin 1은 크기 [1024, 4096) 바이트의 파일을 포함합니다
- Bin 2는 크기 [4096, ∞) 바이트의 파일을 포함합니다

배열 `fileCounts`와 `totalBytes`는 각 bin에 해당하는 파일 수와 총 크기를 각각 저장합니다. 이 데이터 구조는 Delta 테이블의 파일 크기 분포를 효율적으로 분석할 수 있게 합니다.

### 삭제된 레코드 수 히스토그램 스키마

`DeletedRecordCountsHistogram` 객체는 테이블의 파일 전체에서 삭제된 레코드 수 분포를 추적하는 히스토그램을 나타냅니다. 히스토그램의 각 bin은 삭제 수의 범위를 나타내며 해당 수만큼 삭제된 레코드가 있는 파일 수를 저장합니다.

필드 이름 | 데이터 타입 | 설명 | 선택/필수
-|-|-|-
deletedRecordCounts | Array[Long] | 크기 10의 배열로, 각 요소는 특정 삭제 수 범위에 속하는 파일 수를 나타냅니다. | 필수

히스토그램 bin은 다음 범위에 해당합니다:
- Bin 0: [0, 0] (삭제가 없는 파일)
- Bin 1: [1, 9] (1-9개의 삭제된 레코드가 있는 파일)
- Bin 2: [10, 99] (10-99개의 삭제된 레코드가 있는 파일)
- Bin 3: [100, 999] (100-999개의 삭제된 레코드가 있는 파일)
- Bin 4: [1000, 9999] (1,000-9,999개의 삭제된 레코드가 있는 파일)
- Bin 5: [10000, 99999] (10,000-99,999개의 삭제된 레코드가 있는 파일)
- Bin 6: [100000, 999999] (100,000-999,999개의 삭제된 레코드가 있는 파일)
- Bin 7: [1000000, 9999999] (1,000,000-9,999,999개의 삭제된 레코드가 있는 파일)
- Bin 8: [10000000, 2147483646] (10,000,000에서 2147483646(즉, Java의 Int.MaxValue-1)개의 삭제된 레코드가 있는 파일)
- Bin 9: [2147483647, ∞) (2147483647개 이상의 삭제된 레코드가 있는 파일)

이 히스토그램은 Delta 테이블의 파일 전체에서 삭제된 레코드 분포를 분석할 수 있게 하며, 삭제 패턴을 모니터링하고 최적화하는 데 유용할 수 있습니다.

#### 상태 검증

Reader는 다음을 통해 특정 버전에서 테이블 상태 무결성을 검증할 수 있습니다:
1. 해당 버전의 버전 체크섬 파일 읽기
2. 테이블 상태에 대한 [액션 조정](#액션-조정)을 수행하여 동일한 메트릭을 독립적으로 계산
3. 계산된 값을 버전 체크섬에 기록된 값과 비교

계산된 값과 기록된 값 사이에 불일치가 발견되면 해당 버전의 테이블 상태는 잠재적으로 손상된 것으로 간주되어야 합니다.

### Writer 요구사항

- Writer는 각 커밋에 대해 버전 체크섬 파일을 생성해야 합니다(SHOULD)
- Writer는 버전 체크섬의 모든 메트릭이 액션 조정 후 테이블 상태를 정확하게 반영하도록 보장해야 합니다(MUST)
- Writer는 해당 Delta 로그 엔트리를 성공적으로 작성한 후에만 버전 체크섬 파일을 작성해야 합니다(MUST)
- Writer는 기존 버전 체크섬 파일을 덮어쓰지 않아야 합니다(MUST NOT)

### Reader 요구사항

- Reader는 버전 체크섬을 사용하여 테이블 상태 무결성을 검증할 수 있습니다(MAY)
- 검증을 수행하는 경우 Reader는 모든 필수 필드가 계산된 값과 일치하는지 확인해야 합니다(SHOULD)
- 검증이 실패하면 Reader는 오류 메시지를 통해 불일치를 사용자에게 알려야 합니다(SHOULD)
- Reader는 버전 체크섬 파일이 누락된 경우에도 계속 작동해야 합니다(MUST)


## 액션
액션은 테이블의 상태를 수정하며 Delta 파일과 체크포인트 모두에 저장됩니다.
이 섹션에서는 사용 가능한 액션의 공간과 해당 스키마를 나열합니다.

### 메타데이터 변경
`metaData` 액션은 테이블의 현재 메타데이터를 변경합니다.
테이블의 첫 번째 버전에는 `metaData` 액션이 포함되어야 합니다.
후속 `metaData` 액션은 테이블의 현재 메타데이터를 완전히 덮어씁니다.

테이블의 특정 버전에는 최대 하나의 메타데이터 액션이 있을 수 있습니다.

모든 메타데이터 액션은 최소한 필수 필드를 포함**해야** 합니다.

`metaData` 액션의 스키마는 다음과 같습니다:

필드 이름 | 데이터 타입 | 설명 | 선택/필수
-|-|-|-
id|`GUID`|이 테이블의 고유 식별자 | 필수
name|`String`| 이 테이블에 대한 사용자 제공 식별자 | 선택
description|`String`| 이 테이블에 대한 사용자 제공 설명 | 선택
format|[Format Struct](#포맷-사양)| 테이블에 저장된 파일의 인코딩 사양 | 필수
schemaString|[Schema Struct](#스키마-직렬화-형식)| 테이블의 스키마 | 필수
partitionColumns|`Array[String]`| 데이터를 파티션해야 하는 컬럼 이름을 포함하는 배열 | 필수
createdTime|`Option[Long]`| 이 메타데이터 액션이 생성된 시간(Unix epoch 이후 밀리초) | 선택
configuration|`Map[String, String]`| 메타데이터 액션에 대한 구성 옵션을 포함하는 맵 | 필수

#### 포맷 사양
필드 이름 | 데이터 타입 | 설명
-|-|-
provider|`String`|이 테이블의 파일 인코딩 이름
options|`Map[String, String]`|형식에 대한 구성 옵션을 포함하는 맵

참조 구현에서 provider 필드는 Spark SQL [`FileFormat`](https://github.com/apache/spark/blob/master/sql/core/src/main/scala/org/apache/spark/sql/execution/datasources/FileFormat.scala)을 인스턴스화하는 데 사용됩니다. Spark 2.4.3부터 `parquet`, `csv`, `orc`, `json`, `text`에 대한 기본 제공 `FileFormat` 지원이 있습니다.

Delta Lake 0.3.0부터 사용자 대면 API는 `format = 'parquet'`이고 `options = {}`인 테이블 생성만 허용합니다. 다른 형식을 읽기 위한 지원은 레거시 이유와 향후 다른 형식에 대한 가능한 지원을 가능하게 하기 위해 존재합니다([#87](https://github.com/delta-io/delta/issues/87) 참조).

```json

    "id":"af23c9d7-fff1-4a5a-a2c8-55c59bd782aa",
    "format":{"provider":"parquet","options":{}},
    "schemaString":"...",
    "partitionColumns":[],
    "configuration":{
      "appendOnly": "true"
    }
  }
}
```

### 파일 추가 및 파일 제거
`add` 및 `remove` 액션은 개별 _논리적 파일_을 각각 추가하거나 제거하여 테이블의 데이터를 수정하는 데 사용됩니다.

테이블의 모든 _논리적 파일_은 데이터 파일 경로와 테이블에 더 이상 없는 데이터 파일의 행을 나타내는 선택적 삭제 벡터(DV)의 조합으로 표현됩니다. 삭제 벡터는 선택적 기능입니다. 자세한 내용은 [Reader 요구사항](#삭제-벡터)을 참조하세요.

테이블에 이미 존재하는 논리적 파일에 대해 `add` 액션이 발생하면 최신 버전의 통계 및 기타 정보가 이전 버전의 정보를 대체해야 합니다.
파일 집합에서 논리적 파일 엔트리의 기본 키는 데이터 파일의 `path`와 DV를 설명하는 고유 ID의 튜플입니다. DV가 이 논리적 파일의 일부가 아닌 경우 기본 키는 대신 `(path, NULL)`입니다.

`remove` 액션에는 제거가 발생한 시점을 나타내는 타임스탬프가 포함됩니다.
물리적 파일의 물리적 삭제는 사용자가 지정한 만료 시간 임계값 이후 지연되어 발생할 수 있습니다.
이러한 지연을 통해 동시 Reader가 데이터의 오래된 스냅샷에 대해 계속 실행할 수 있습니다.
`remove` 액션은 만료될 때까지 _툼스톤_으로 테이블 상태에 남아 있어야 합니다.
툼스톤은 *현재 시간*(정리를 수행하는 노드에 따라)이 `remove` 액션 타임스탬프에 추가된 만료 임계값을 초과할 때 만료됩니다.

다음 설명에서 `dvId`는 특정 삭제 벡터의 고유 ID(`deletionVector.uniqueId`) 또는 `NULL`을 참조할 수 있으며, 무효화된 행이 없음을 나타냅니다. 주어진 Delta 커밋 내의 액션이 순서대로 적용된다고 보장되지 않기 때문에 **유효한** 버전은 `path`와 `dvId`의 조합에 대해 *동일한 타입*(즉, `add`/`remove`)의 파일 액션을 최대 하나 포함하도록 제한됩니다. 또한 단순성을 위해 `path`에 대해 동일한 타입의 파일 액션이 최대 하나(`dvId`와 관계없이) 있어야 합니다.
즉, 모든 커밋에 대해...

- 동일한 `path`가 `add` 액션과 `remove` 액션에 나타나지만 두 개의 다른 `dvId`를 사용하는 것은 **합법적**입니다.
- 동일한 `path`가 추가 및/또는 제거되고 `cdc` 액션에도 나타나는 것은 **합법적**입니다.
- 동일한 `path`가 `add` 또는 `remove` 액션 집합 내에서 다른 `dvId`로 두 번 나타나는 것은 **불법**입니다.
- 커밋에 나중 조합에 대한 제거도 포함하지 않는 한, 커밋 직전 버전의 스냅샷에서 `add` 액션 목록의 다른 `dvId`로 이미 나타나는 `path`를 `add` 액션에서 커밋하는 것은 **불법**입니다.
- 기존 `path`와 `dvId` 조합을 다시 커밋하는 것은 **합법적**입니다(메타데이터 업데이트를 허용).

`add` 또는 `remove`의 `dataChange` 플래그는 동일한 원자적 버전의 다른 액션과 결합될 때 기존 데이터를 재배열하거나 새 통계만 추가하는 액션을 나타내기 위해 `false`로 설정될 수 있습니다.
예를 들어 트랜잭션 로그를 추적하는 스트리밍 쿼리는 이 플래그를 사용하여 최종 결과에 영향을 미치지 않는 액션을 건너뛸 수 있습니다.

`add` 액션의 스키마는 다음과 같습니다:

필드 이름 | 데이터 타입 | 설명 | 선택/필수
-|-|-|-
path| String | 테이블 루트에서 데이터 파일까지의 상대 경로 또는 테이블에 추가해야 하는 파일의 절대 경로. 경로는 [RFC 2396 URI Generic Syntax](https://www.ietf.org/rfc/rfc2396.txt)에 지정된 URI이며 데이터 파일 경로를 얻으려면 디코딩해야 합니다. | 필수
partitionValues| Map[String, String] | 이 논리적 파일에 대한 파티션 컬럼에서 값으로의 맵. [파티션 값 직렬화](#파티션-값-직렬화)도 참조하세요. | 필수
size| Long | 이 데이터 파일의 크기(바이트) | 필수
modificationTime | Long | 이 논리적 파일이 생성된 시간(epoch 이후 밀리초) | 필수
dataChange | Boolean | `false`일 때 논리적 파일은 테이블에 이미 존재해야 하거나 추가된 파일의 레코드가 동일한 버전의 하나 이상의 `remove` 액션에 포함되어야 합니다 | 필수
stats | [Statistics Struct](#파일별-통계) | 이 논리적 파일의 데이터에 대한 통계(예: 개수, 컬럼의 최소/최대 값) 포함 | 선택

### CDC 파일 추가
`cdc` 액션은 트랜잭션의 일부로 변경된 데이터만 포함하는 [파일](#변경-데이터-파일)을 추가하는 데 사용됩니다. `cdc` 액션은 복사된 행을 포함하지 않고 모든 행에 대해 `_change_type` 컬럼이 채워진 경우 `add` 액션으로도 추가되는 [데이터 파일](#데이터-파일)을 추가할 수 있습니다.

변경 데이터 Reader가 특정 Delta 테이블 버전에서 `cdc` 액션을 발견하면 해당 버전에서 수행된 변경 사항을 `cdc` 파일만 사용하여 읽어야 합니다. 버전에 `cdc` 액션이 없는 경우 `add` 및 `remove` 액션의 데이터는 각각 삽입되고 삭제된 행으로 읽힙니다.

`cdc` 액션의 스키마는 다음과 같습니다:

필드 이름 | 데이터 타입 | 설명
-|-|-
path| String | 테이블 루트에서 변경 데이터 파일까지의 상대 경로 또는 테이블에 추가해야 하는 변경 데이터 파일의 절대 경로. 경로는 [RFC 2396 URI Generic Syntax](https://www.ietf.org/rfc/rfc2396.txt)에 지정된 URI이며 파일 경로를 얻으려면 디코딩해야 합니다.
partitionValues| Map[String, String] | 이 파일에 대한 파티션 컬럼에서 값으로의 맵. [파티션 값 직렬화](#파티션-값-직렬화)도 참조하세요.
size| Long | 이 파일의 크기(바이트)
dataChange | Boolean | `cdc` 액션의 경우 테이블의 기본 데이터를 변경하지 _않기_ 때문에 항상 `false`로 설정되어야 합니다
tags | Map[String, String] | 이 파일에 대한 메타데이터를 포함하는 맵

다음은 `cdc` 액션의 예입니다.

```json
{
  "cdc": {
    "path": "_change_data/cdc-00001-c…..snappy.parquet",
    "partitionValues": {},
    "size": 1213,
    "dataChange": false
  }
}
```

#### AddCDCFile에 대한 Writer 요구사항

[Writer 버전 4에서 6까지](#writer-버전-요구사항)의 경우 모든 Writer는 테이블 메타데이터의 `delta.enableChangeDataFeed` 구성 플래그를 준수해야 합니다. `delta.enableChangeDataFeed`가 `true`일 때 Writer는 [변경 데이터 파일](#변경-데이터-파일)에 지정된 대로 데이터를 변경하는 모든 작업에 대해 관련 `AddCDCFile`을 생성해야 합니다.

Writer 버전 7의 경우 모든 Writer는 테이블 `protocol`의 `writerFeatures`에 `changeDataFeed` 기능이 존재하는 경우에만 테이블 메타데이터의 `delta.enableChangeDataFeed` 구성 플래그를 준수해야 합니다.

#### AddCDCFile에 대한 Reader 요구사항

사용 가능한 경우 변경 데이터 Reader는 `add` 및 `remove` 액션이 참조하는 기본 데이터 파일에서 변경 사항을 계산하는 대신 주어진 테이블 버전의 `cdc` 액션을 사용해야 합니다.
특히 버전에서 수행된 행 수준 변경 사항을 읽으려면 다음 전략을 사용해야 합니다:
1. 이 버전에 `cdc` 액션이 있는 경우 행 수준 변경 사항을 얻기 위해 해당 액션만 읽고 이 버전의 나머지 `add` 및 `remove` 액션을 건너뜁니다.
2. 그렇지 않으면 이 버전에 `cdc` 액션이 없는 경우 `add` 및 `remove` 액션의 모든 행을 각각 삽입되고 삭제된 행으로 읽고 처리합니다.
3. 변경 데이터 Reader는 다음 추가 컬럼을 반환해야 합니다:

    필드 이름 | 데이터 타입 | 설명
       -|-|-
    _commit_version|`Long`| 변경 사항을 포함하는 테이블 버전. 액션을 포함하는 Delta 로그 파일 이름에서 파생될 수 있습니다.
    _commit_timestamp|`Timestamp`| 커밋이 생성될 때 연결된 타임스탬프. [In-Commit Timestamps](#in-commit-timestamps)가 활성화되었는지 여부에 따라 버전의 Delta 로그 파일의 `commitInfo` 액션의 `inCommitTimestamp` 필드 또는 Delta 로그 파일의 수정 시간에서 파생됩니다.

##### 비변경 데이터 Reader에 대한 참고 사항

Change Data Feed가 활성화된 테이블에서 `add` 및 `remove` 액션이 참조하는 데이터 Parquet 파일에는 추가 컬럼 `_change_type`이 포함될 수 있습니다. 이 컬럼은 테이블 스키마에 없습니다. 이러한 파일에 액세스할 때 Reader는 이 컬럼을 무시하고 테이블 스키마 내에 정의된 컬럼만 처리해야 합니다.

### 트랜잭션 식별자
자체 애플리케이션별 버전을 사용하여 진행 상황을 추적하는 증분 처리 시스템(예: 스트리밍 시스템)은 쓰기 중 실패 및 재시도 시 데이터 중복을 방지하기 위해 어떤 진행이 이루어졌는지 기록해야 합니다.
트랜잭션 식별자를 사용하면 이 정보를 테이블 내용을 수정하는 다른 액션과 함께 Delta 테이블의 트랜잭션 로그에 원자적으로 기록할 수 있습니다.

트랜잭션 식별자는 `appId` `version` 쌍의 형태로 저장되며, 여기서 `appId`는 테이블을 수정하는 프로세스의 고유 식별자이고 `version`은 해당 애플리케이션이 얼마나 진행했는지를 나타냅니다.
이 정보를 테이블 수정과 함께 원자적으로 기록하면 이러한 외부 시스템이 Delta 테이블에 대한 쓰기를 _멱등적_으로 만들 수 있습니다.

예를 들어 Apache Spark의 Structured Streaming을 위한 [Delta Sink](https://github.com/delta-io/delta/blob/master/core/src/main/scala/org/apache/spark/sql/delta/sources/DeltaSink.scala)는 다음 프로세스를 사용하여 테이블에 스트림을 쓸 때 정확히 한 번 의미론을 보장합니다:
1. 쓸 데이터와 이 배치에 대한 단조 증가 식별자를 write-ahead-log에 기록합니다.
2. 대상 테이블에서 `appId = streamId`인 트랜잭션의 현재 버전을 확인합니다. 이 값이 작성 중인 배치보다 크거나 같으면 이 데이터가 이미 테이블에 추가된 것이므로 처리를 다음 배치로 건너뜁니다.
3. 낙관적으로 테이블에 데이터를 씁니다.
4. 작성된 데이터 추가와 업데이트된 `appId` `version` 쌍을 모두 포함하는 트랜잭션을 커밋하려고 시도합니다.

애플리케이션별 `version`의 의미론은 외부 시스템에 맡겨집니다.
Delta는 주어진 `appId`에 대한 최신 `version`이 테이블 스냅샷에서 사용 가능하도록 보장합니다.
Delta 트랜잭션 프로토콜은 예를 들어 `version`의 단조성을 가정하지 않으며 `version`이 감소하여 이전 트랜잭션의 "롤백"을 나타낼 수 있습니다.

`txn` 액션의 스키마는 다음과 같습니다:

필드 이름 | 데이터 타입 | 설명 | 선택/필수
-|-|-|-
appId | String | 트랜잭션을 수행하는 애플리케이션의 고유 식별자 | 필수
version | Long | 이 트랜잭션에 대한 애플리케이션별 숫자 식별자 | 필수
lastUpdated | Option[Long] | 이 트랜잭션 액션이 생성된 시간(Unix epoch 이후 밀리초) | 선택

다음은 `txn` 액션의 예입니다:
```json
{
  "txn": {
    "appId":"3ba13872-2d47-4e17-86a0-21afd2a22395",
    "version":364475
  }
}
```

### 프로토콜 진화
`protocol` 액션은 주어진 테이블을 읽거나 쓰는 데 필요한 Delta 프로토콜 버전을 높이는 데 사용됩니다.
프로토콜 버전 관리를 통해 최신 클라이언트는 트랜잭션 로그를 올바르게 해석하는 데 필요한 기능이 누락된 이전 Reader 및/또는 Writer를 제외할 수 있습니다.
_프로토콜 버전_은 이 사양에 대해 호환되지 않는 변경 사항이 발생할 때마다 증가합니다.
클라이언트가 잘못된 프로토콜 버전을 실행하는 경우 사용자에게 Delta 클라이언트 라이브러리의 최신 프로토콜 버전으로 업그레이드하도록 지시하는 오류가 발생해야 합니다.

중단 변경 사항은 테이블에 기록된 프로토콜 버전의 증가 또는 테이블 기능의 추가를 동반해야 하므로 클라이언트는 인식할 수 없는 액션, 필드 및/또는 메타데이터 도메인이 트랜잭션 로그를 올바르게 해석하는 데 필요하지 않다고 가정할 수 있습니다. 클라이언트는 인식할 수 없는 필드를 무시해야 하며 인식할 수 없는 필드가 포함된 테이블을 읽을 때 오류를 생성해서는 안 됩니다.

Reader 버전 3과 Writer 버전 7은 프로토콜 액션에 두 개의 테이블 기능 목록을 추가합니다. 이러한 테이블에서 Reader와 Writer가 작동할 수 있는 능력은 지원되는 프로토콜 버전뿐만 아니라 `readerFeatures`와 `writerFeatures`에 나열된 모든 기능을 지원하는지 여부에 따라 달라집니다. 자세한 내용은 [테이블 기능](#테이블-기능) 섹션을 참조하세요.

`protocol` 액션의 스키마는 다음과 같습니다:

필드 이름 | 데이터 타입 | 설명 | 선택/필수
-|-|-|-
minReaderVersion | Int | 이 테이블을 올바르게 *읽기* 위해 클라이언트가 구현해야 하는 Delta 읽기 프로토콜의 최소 버전 | 필수
minWriterVersion | Int | 이 테이블을 올바르게 *쓰기* 위해 클라이언트가 구현해야 하는 Delta 쓰기 프로토콜의 최소 버전 | 필수
readerFeatures | Array[String] | 이 테이블을 올바르게 읽기 위해 클라이언트가 구현해야 하는 기능 모음(`minReaderVersion`이 `3`으로 설정된 경우에만 존재) | 선택
writerFeatures | Array[String] | 이 테이블을 올바르게 쓰기 위해 클라이언트가 구현해야 하는 기능 모음(`minWriterVersion`이 `7`로 설정된 경우에만 존재) | 선택

일부 Delta 프로토콜 예:
```json
{
  "protocol":{
    "minReaderVersion":1,
    "minWriterVersion":2
  }
}
```

Writer에 대해서만 테이블 기능을 사용하는 테이블:
```json
{
  "protocol":{
    "readerVersion":2,
    "writerVersion":7,
    "writerFeatures":["columnMapping","identityColumns"]
  }
}
```
위 예제의 Reader 버전 2는 Reader 기능 나열을 지원하지 않지만 컬럼 매핑을 지원합니다. 이 예제는 컬럼 매핑이 Reader 테이블 기능으로 표현되는 다음 예제와 동일합니다.

Reader와 Writer 모두에 대해 테이블 기능을 사용하는 테이블:
```json
{
  "protocol": {
    "readerVersion":3,
    "writerVersion":7,
    "readerFeatures":["columnMapping"],
    "writerFeatures":["columnMapping","identityColumns"]
  }
}
```

### 도메인 메타데이터
도메인 메타데이터 액션에는 명명된 메타데이터 도메인에 대한 구성(문자열)이 포함됩니다. 두 개의 겹치는 트랜잭션은 둘 다 동일한 메타데이터 도메인에 대한 도메인 메타데이터 액션을 포함하는 경우 충돌합니다.

두 가지 유형의 메타데이터 도메인이 있습니다:
1. **사용자 제어 메타데이터 도메인**은 `delta.` 접두사 이외의 것으로 시작하는 이름을 갖습니다. 모든 Delta 클라이언트 구현 또는 사용자 애플리케이션이 이러한 메타데이터 도메인을 수정할 수 있으며 사용자가 임의로 수정할 수 있도록 허용할 수 있습니다. Delta 클라이언트 및 사용자 애플리케이션은 다른 클라이언트나 사용자의 메타데이터 도메인과 충돌을 방지하기 위해 명명 규칙을 사용하는 것이 권장됩니다(예: `com.databricks.*` 또는 `org.apache.*`).
2. **시스템 제어 메타데이터 도메인**은 `delta.` 접두사로 시작하는 이름을 갖습니다. 이 접두사는 Delta 사양에서 정의한 메타데이터 도메인용으로 예약되어 있으며 Delta 클라이언트 구현은 사용자가 시스템 제어 도메인의 메타데이터를 수정하도록 허용해서는 안 됩니다. Delta 클라이언트 구현은 알고 이해하는 시스템 제어 도메인의 메타데이터만 업데이트해야 합니다. 시스템 제어 메타데이터 도메인은 다양한 테이블 기능에서 사용되며 각 테이블 기능은 사용하는 메타데이터 도메인에 추가 의미론을 부과할 수 있습니다.

`domainMetadata` 액션의 스키마는 다음과 같습니다:

필드 이름 | 데이터 타입 | 설명
-|-|-
domain | String | 이 도메인의 식별자(시스템 또는 사용자 제공)
configuration | String | 메타데이터 도메인에 대한 구성을 포함하는 문자열
removed | Boolean | `true`일 때 액션은 메타데이터 도메인을 논리적으로 삭제하는 툼스톤 역할을 합니다. Writer는 구성의 정확한 사전 이미지를 보존해야 합니다.

이 기능을 지원하려면:
- 테이블은 Writer 버전 7이어야 합니다.
- 테이블의 `writerFeatures`에 `domainMetadata` 기능 이름이 존재해야 합니다.

#### 도메인 메타데이터에 대한 Reader 요구사항
- Reader는 도메인 메타데이터를 지원할 필요가 없습니다.
- 도메인 메타데이터를 지원하지 않는 Reader는 메타데이터 도메인 액션을 인식할 수 없는 것으로 무시해야 하며([프로토콜 진화](#프로토콜-진화) 참조) 스냅샷에는 메타데이터 도메인이 포함되지 않아야 합니다.
- 도메인 메타데이터를 지원하는 Reader는 모든 메타데이터 도메인에 [액션 조정](#액션-조정)을 적용해야 하며 스냅샷에는 이해하지 못하더라도 포함되어야 합니다.
- Reader에 요구사항을 부과하는 시스템 제어 도메인은 [중단 변경](#프로토콜-진화)이며 원하는 동작을 지정하는 Reader-Writer 테이블 기능의 일부여야 합니다.

#### 도메인 메타데이터에 대한 Writer 요구사항
- Writer는 이해하지 못하더라도 모든 도메인을 보존해야 합니다.
- Writer는 사용자가 시스템 제어 도메인을 수정하거나 삭제하도록 허용해서는 안 됩니다.
- Writer는 이해하는 시스템 제어 도메인만 수정하거나 삭제해야 합니다.
- Writer에 추가 요구사항을 부과하는 시스템 제어 도메인은 [중단 변경](#프로토콜-진화)이며 원하는 동작을 지정하는 Writer 테이블 기능의 일부여야 합니다.

다음은 `domainMetadata` 액션의 예입니다:
```json
{
  "domainMetadata": {
    "domain": "delta.deltaTableFeatureX",
    "configuration": "{\"key1\":\"value1\"}",
    "removed": false
  }
}
```

# 액션 조정
테이블의 특정 스냅샷은 커밋 버전을 오름차순으로 테이블에 커밋된 이벤트를 재생하여 계산할 수 있습니다. Delta 테이블의 특정 스냅샷은 다음으로 구성됩니다:

- 단일 `protocol` 액션
- 단일 `metaData` 액션
- 고유한 `appId`를 가진 `txn` 액션 모음
- 고유한 `domain`을 가진 `domainMetadata` 액션 모음
- 고유한 경로 키를 가진 `add` 액션 모음으로, 각 경로에 대해 발견된 최신 (path, deletionVector.uniqueId) 쌍에 해당합니다.
- 고유한 `(path, deletionVector.uniqueId)` 키를 가진 `remove` 액션 모음. `add` 모음과 `remove` 모음의 기본 키 교집합은 비어 있어야 합니다. 즉, 논리적 파일은 `remove`와 `add` 모음에 동시에 존재할 수 없습니다. 그러나 동일한 *데이터 파일*은 *다른* DV와 함께 `remove` 모음에 존재할 수 있습니다. 논리적으로 다른 내용을 나타내기 때문입니다. `remove` 액션은 _툼스톤_으로 작동하며 VACUUM 명령의 이익을 위해서만 존재합니다. 스냅샷 읽기는 읽기 경로에서 `add` 액션만 반환합니다.

위의 요구 사항을 달성하기 위해 다른 Delta 파일의 관련 액션을 서로 조정해야 합니다:

- 마지막에 표시된 최신 `protocol` 액션이 유효합니다
- 마지막에 표시된 최신 `metaData` 액션이 유효합니다
- `txn` 액션의 경우 주어진 `appId`에 대해 표시된 최신 `version`이 유효합니다
- `domainMetadata`의 경우 주어진 `domain`에 대해 표시된 최신 `domainMetadata`가 유효합니다. `removed=true`인 액션은 이전 버전을 억제하는 툼스톤 역할을 합니다. 스냅샷 읽기는 제거된 `domainMetadata` 액션을 반환하지 _않습니다_.
- `commitInfo` 액션의 경우 스냅샷 버전의 커밋에서 `commitInfo`만 스냅샷에 포함됩니다. [체크포인트](#체크포인트)와 [로그 압축 파일](#로그-압축-파일)은 `commitInfo` 액션을 보존하지 않으므로 이 정보는 스냅샷 버전의 JSON 커밋 파일에서 읽어야 합니다.
- 테이블의 논리적 파일은 `(path, deletionVector.uniqueId)` 기본 키로 식별됩니다. 파일 액션(`add` 또는 `remove`)은 논리적 파일을 참조하며 로그에는 단일 파일에 대한 참조가 몇 개든 포함될 수 있습니다.
- 로그를 재생하려면 모든 파일 액션을 스캔하고 각 논리적 파일에 대한 최신 참조만 유지합니다.
- 결과의 `add` 액션은 테이블에 현재 존재하는 논리적 파일을 식별합니다(쿼리용). 결과의 `remove` 액션은 테이블에 더 이상 존재하지 않는 논리적 파일의 툼스톤을 식별합니다(VACUUM용).
- [v2 체크포인트 사양](#v2-사양) 액션은 일반 커밋 파일에서 허용되지 않으며 로그 재생에 참여하지 않습니다.

# 테이블 기능
테이블 기능은 지원되는 프로토콜 버전이 있는 테이블에만 존재해야 합니다. 테이블의 Reader 버전이 3인 경우 `readerFeatures`가 `protocol` 액션에 존재해야 하며, Writer 버전이 7인 경우 `writerFeatures`가 `protocol` 액션에 존재해야 합니다. `readerFeatures`와 `writerFeatures`는 이 테이블을 읽고 쓰기 위해 Reader와 Writer가 구현해야 하는 기능을 정의합니다.

Reader와 Writer는 테이블 기능이 존재할 때 이를 무시해서는 안 됩니다:
- 테이블을 읽으려면 Reader는 `readerFeatures`에 나열된 모든 기능을 구현하고 존중해야 합니다.
- 테이블을 쓰려면 Writer는 `writerFeatures`에 나열된 모든 기능을 구현하고 존중해야 합니다. Writer는 쓰기 전에 테이블(또는 Delta 로그만)을 읽어야 하므로 모든 Reader 기능도 구현하고 존중해야 합니다.

## 새 테이블 및 기존 테이블의 테이블 기능
새 테이블을 만들거나 기존 테이블을 테이블 기능 사용을 지원하는 프로토콜 버전으로 업그레이드할 수 있습니다. 테이블은 Writer 기능 또는 Reader와 Writer 기능 모두의 사용을 지원해야 합니다. Reader는 지원하지만 Writer 기능은 지원하지 않는 것은 불법입니다.

새 테이블의 경우, Reader 버전이 최대 2이고 Writer 버전이 7인 새 테이블을 만들 때 `protocol` 액션에는 `writerFeatures`만 포함되어야 합니다. Reader 버전 3과 Writer 버전 7로 새 테이블을 만들 때 `protocol` 액션에는 `readerFeatures`와 `writerFeatures`가 모두 포함되어야 합니다. Reader 버전 3과 Writer 버전 7 미만으로 테이블을 만드는 것은 허용되지 않습니다.

기존 테이블을 Reader 버전 3 및/또는 Writer 버전 7로 업그레이드할 때 클라이언트는 최선을 다해 원래 프로토콜 버전에서 지원하는 기능 중 테이블의 과거 버전에서 사용된 기능을 결정하고 사용된 기능만 Reader 및/또는 Writer 기능 집합에 추가해야 합니다. 클라이언트는 시간 여행으로 도달할 수 있는 테이블의 과거 버전에서 기능이 *확실히* 사용되지 않았음을 증명할 수 없는 한 기능이 사용되었다고 가정해야 합니다.

예를 들어 Reader 버전 1과 Writer 버전 4의 테이블과 네 가지 버전이 주어진 경우:
1. 테이블 속성 변경: `delta.enableChangeDataFeed`를 `true`로 설정.
2. 데이터 변경: 세 행 업데이트.
3. 테이블 속성 변경: `delta.enableChangeDataFeed` 해제.
4. 테이블 프로토콜 변경: 프로토콜을 Reader 버전 3과 Writer 버전 7로 업그레이드.

버전 4를 생성하기 위해 Writer는 버전 3만 보고 Change Data Feed가 사용되지 않았음을 발견할 수 있습니다. 그러나 실제로 이 기능은 사용되었으며 테이블에는 버전 2에 대한 일부 Change Data Files가 포함되어 있습니다. 즉, 테이블에서 사용된 모든 기능을 결정하려면 Writer는 전체 히스토리를 스캔하거나(매우 시간이 많이 걸림) 최악의 경우를 가정해야 합니다: 프로토콜 `(1, 4)`에서 지원하는 모든 기능이 사용되었습니다.

## 지원되는 기능
기능은 `protocol` 액션의 `readerFeatures` 및/또는 `writerFeatures`에 이름이 있을 때 테이블에서 지원됩니다. 이 테이블에 대한 후속 읽기 및/또는 쓰기 작업은 기능을 존중해야 합니다. 클라이언트는 `protocol` 액션에서 기능을 제거해서는 안 됩니다.

Writer는 `readerFeatures` 또는 `writerFeatures`에 이름을 추가하여 테이블에 기능 지원을 추가할 수 있습니다. Reader 기능은 `readerFeatures`와 `writerFeatures`에 동시에 나열되어야 하며, Writer 기능은 `writerFeatures`에만 나열되어야 합니다. `readerFeatures`에만 기능을 나열하고 `writerFeatures`에는 나열하지 않는 것은 허용되지 않습니다.

기능이 지원된다고 해서 활성화되었다는 의미는 아닙니다. 예를 들어 테이블에는 `writerFeatures`에 [추가 전용 테이블](#추가-전용-테이블) 기능(기능 이름 `appendOnly`)이 나열되어 있지만 `delta.appendOnly`가 `true`로 설정된 테이블 속성이 없을 수 있습니다. 이 경우 테이블은 추가 전용이 아니며 Writer는 데이터를 변경, 제거, 재배열할 수 있습니다. 그러나 Writer는 테이블을 쓰기 전에 `delta.appendOnly` 테이블 속성을 확인해야 한다는 것을 알아야 합니다.

## 활성 기능
기능은 지원*되고* 메타데이터 요구 사항이 충족될 때 테이블에서 활성화됩니다. 각 기능은 이 문서의 해당 섹션에 명시된 대로 자체 메타데이터 요구 사항을 정의합니다. 예를 들어 추가 전용 기능은 `protocol`의 `writerFeatures`에 `appendOnly` 기능 이름이 있*고* `delta.appendOnly`가 `true`로 설정된 테이블 속성이 있을 때 활성화됩니다.

# 컬럼 매핑
Delta는 컬럼 매핑을 사용하여 컬럼 명명 제한을 피하고 모든 데이터를 다시 작성하지 않고도 컬럼 이름 변경 및 삭제를 지원할 수 있습니다. 컬럼 매핑에는 `name`과 `id`의 두 가지 모드가 있습니다. 두 모드 모두에서 중첩 또는 리프 컬럼 모두에 고유한 _물리적_ 이름과 32비트 정수로 고유 ID가 할당됩니다. 물리적 이름은 `delta.columnMapping.physicalName` 키와 함께 컬럼 메타데이터의 일부로 저장됩니다. 컬럼 ID는 `delta.columnMapping.id` 키와 함께 메타데이터 내에 저장됩니다.

컬럼 매핑은 `none`, `id`, `name` 중 하나인 테이블 속성 `delta.columnMapping.mode`로 제어됩니다. 테이블 속성은 테이블의 프로토콜에 `columnMapping` 테이블 기능을 지원하는 Reader 및 Writer 버전 및/또는 테이블 기능이 있는 경우에만 존중되어야 합니다. Reader의 경우 이는 Reader 버전 2 또는 `columnMapping` 테이블 기능이 지원되는 것으로 나열된 Reader 버전 3입니다. Writer의 경우 이는 Writer 버전 5 또는 6, 또는 `columnMapping` 테이블 기능이 지원되는 Writer 버전 7입니다.

다음은 컬럼 매핑을 활용하는 테이블의 컬럼 정의 예입니다. 더 완전한 스키마 정의는 [부록](#스키마-직렬화-형식)을 참조하세요.
```json
{
    "name" : "e",
    "type" : {
      "type" : "array",
      "elementType" : {
        "type" : "struct",
        "fields" : [ {
          "name" : "d",
          "type" : "integer",
          "nullable" : false,
          "metadata" : { 
            "delta.columnMapping.id": 5,
            "delta.columnMapping.physicalName": "col-a7f4159c-53be-4cb0-b81a-f7e5240cfc49"
          }
        } ]
      },
      "containsNull" : true
    },
    "nullable" : true,
    "metadata" : { 
      "delta.columnMapping.id": 4,
      "delta.columnMapping.physicalName": "col-5f422f40-de70-45b2-88ab-1d5c90e94db1"
    }
  }
```

## 컬럼 매핑에 대한 Writer 요구사항
컬럼 매핑을 지원하려면 Writer는 다음을 수행해야 합니다:
- 컬럼 매핑이 처음 활성화될 때 `protocol` 및 `metaData` 액션을 작성합니다:
    - 테이블이 Writer 버전 5 또는 6인 경우: `delta.columnMapping.mode` 테이블 속성을 추가하기 위해 `metaData` 액션을 작성합니다.
    - 테이블이 Writer 버전 7인 경우:
        - `readerFeatures`와 `writerFeatures` 모두에 `columnMapping` 기능을 추가하기 위해 `protocol` 액션을 작성하고,
        - `delta.columnMapping.mode` 테이블 속성을 추가하기 위해 `metaData` 액션을 작성합니다.
- 각 컬럼에 대해 선택된 _물리적 이름_을 사용하여 데이터 파일을 작성합니다. 컬럼의 물리적 이름은 정적이며 변경 가능한 컬럼의 _표시 이름_과 다를 수 있습니다.
- [Parquet Thrift 사양](https://github.com/apache/parquet-format/blob/master/src/main/thrift/parquet.thrift)의 `SchemaElement` struct의 `field_id` 필드의 일부로 32비트 정수 컬럼 식별자를 작성합니다.
- 트랜잭션 로그에서 컬럼의 물리적 이름으로 파티션 값과 컬럼 수준 통계를 추적합니다.
- 스키마에 추가되는 각 새 컬럼에 대해 전역적으로 고유한 식별자를 물리적 이름으로 할당합니다. 이는 `name` 모드에서 저렴한 컬럼 삭제를 지원하는 데 특히 중요합니다. 또한 각 컬럼에 컬럼 식별자를 할당해야 합니다. 컬럼에 할당된 최대 ID는 테이블 속성 `delta.columnMapping.maxColumnId`로 추적됩니다. 이는 사용자가 구성할 수 없는 내부 테이블 속성입니다. 이 값은 새 컬럼이 도입되고 스키마에 새 컬럼을 도입하는 것과 함께 테이블에 커밋될 때 단조롭게 증가해야 합니다.

## 컬럼 매핑에 대한 Reader 요구사항
테이블이 Reader 버전 2에 있거나 테이블이 Reader 버전 3에 있고 `readerFeatures`에 `columnMapping` 기능이 있는 경우 Reader와 Writer는 테이블 속성 `delta.columnMapping.mode`를 읽고 다음 중 하나를 수행해야 합니다.

`none` 모드이거나 테이블 속성이 없는 경우 Reader는 스키마의 컬럼 정의의 표시 이름(`name` 필드)을 사용하여 parquet 파일을 읽어야 합니다.

`id` 모드에서 Reader는 Delta 스키마의 컬럼 메타데이터 속성 `delta.columnMapping.id`에서 제공한 대로 각 파일의 parquet 메타데이터에서 `field_id`를 사용하여 컬럼을 해결해야 합니다. 파티션 값과 컬럼 수준 통계는 트랜잭션 로그의 각 `add` 엔트리에 대해 *물리적 이름*으로 해결되어야 합니다. 데이터 파일에 필드 ID가 없는 경우 Reader는 해당 파일 읽기를 거부하거나 각 컬럼에 대해 null을 반환해야 합니다. 파일에서 찾을 수 없는 ID의 경우 Reader는 해당 컬럼에 대해 `null` 값을 반환해야 합니다.

`name` 모드에서 Reader는 Delta 스키마의 컬럼 메타데이터 속성 `delta.columnMapping.physicalName`에서 제공한 대로 물리적 이름으로 데이터 파일의 컬럼을 해결해야 합니다. 파티션 값과 컬럼 수준 통계도 물리적 이름으로 해결됩니다. 파일에서 찾을 수 없는 컬럼의 경우 `null`을 반환해야 합니다. 이 모드에서는 해결 목적으로 컬럼 ID가 사용되지 않습니다.

# 삭제 벡터
이 기능을 지원하려면:
- 삭제 벡터를 지원하려면 테이블에 Reader 버전 3과 Writer 버전 7이 있어야 합니다. 테이블의 `readerFeatures` 및 `writerFeatures`에 `deletionVectors` 기능 이름이 존재해야 합니다.

지원되는 경우:
- 테이블은 Delta 스키마에 `delta.enableDeletionVectors` 메타데이터 속성이 `true`로 설정되어 있을 수 있습니다. Writer는 이 속성이 `true`로 설정된 경우에만 새 삭제 벡터(DV)를 작성해야 합니다.
- 테이블의 `add` 및 `remove` 액션은 선택적으로 논리적으로 삭제된 행에 대한 정보를 제공하는 DV를 포함할 수 있습니다. 그러나 이러한 행은 여전히 기본 데이터 파일에 물리적으로 존재하며 처리 중에 건너뛰어야 합니다. Reader는 `delta.enableDeletionVectors` 테이블 속성이 설정되지 않은 경우에도 DV의 존재를 고려하여 테이블을 읽어야 합니다.

DV는 `storageType` 필드로 표시되는 다양한 방식으로 저장되고 액세스될 수 있습니다. Delta 프로토콜은 현재 인라인 또는 디스크 저장을 지원하며, 후자는 UUID에서 파생된 상대 경로 또는 절대 경로로 액세스할 수 있습니다.

## 삭제 벡터 디스크립터 스키마

`DeletionVectorDescriptor` struct의 스키마는 다음과 같습니다:

필드 이름 | 데이터 타입 | 설명
-|-|-
storageType | String | DV에 액세스하는 방법을 나타내는 단일 문자. 유효한 옵션: `['u', 'i', 'p']`.
pathOrInlineDv | String | 현재 세 가지 형식 옵션이 제안됩니다:<ul><li>`storageType = 'u'`인 경우 `<랜덤 접두사 - 선택><base85 인코딩된 uuid>`: 삭제 벡터는 이 Delta 테이블의 데이터 디렉토리에 상대적인 경로의 파일에 저장되며 파일 이름은 UUID에서 재구성할 수 있습니다. 파일 이름을 재구성하는 방법은 파생 필드를 참조하세요. 랜덤 접두사는 (20자 고정 길이) uuid 앞의 추가 문자로 복구됩니다.</li><li>`storageType = 'i'`인 경우 `<base85 인코딩된 바이트>`: 삭제 벡터는 로그에 인라인으로 저장됩니다. 사용되는 형식은 DV가 디스크에 저장될 때도 사용되고 [삭제 벡터 형식](#삭제-벡터-형식)에 설명된 `RoaringBitmapArray` 형식입니다.</li><li>`storageType = 'p'`인 경우 `<절대 경로>`: DV는 `add`/`remove` 액션의 `path` 필드와 동일한 형식을 가진 이 경로로 제공된 절대 경로의 파일에 저장됩니다.</li></ul>
offset | Option[Int] | 이 DV가 저장된 파일의 시작 부분에서 이 DV에 대한 데이터의 시작(바이트 수). `storageType = 'i'`일 때 항상 `None`(JSON에서 없음).
sizeInBytes | Int | 직렬화된 DV의 크기(바이트)(원시 데이터 크기, 즉 인라인인 경우 base85 인코딩 전).
cardinality | Long | 주어진 DV가 파일에서 논리적으로 제거하는 행 수.

사용되는 구체적인 Base85 변형은 JSON 친화적이기 때문에 [Z85](https://rfc.zeromq.org/spec/32/)입니다.

### 파생 필드

DV를 사용하는 데 필요하지만 명시적으로 저장되지 않는 일부 필드는 저장된 필드에서 코드로 파생될 수 있습니다.

필드 이름 | 데이터 타입 | 설명 | 계산 방법
-|-|-|-
uniqueId | String | 주어진 파일에 대한 DV를 고유하게 식별합니다. 연속 버전에서 다른 DV를 가진 동일한 파일을 구별하기 위해 스냅샷 재구성에 사용됩니다. | `offset`이 `None`이면 `<storageType><pathOrInlineDv>`. <br> 그렇지 않으면 `<storageType><pathOrInlineDv>@<offset>`.
absolutePath | String/URI/Path | DV 파일의 절대 경로. 상위 디렉토리 경로를 제공하여 상대 경로 DV에 대해 계산할 수 있습니다. | `storageType='p'`인 경우 이미 절대 경로를 사용합니다. `storageType='u'`인 경우 DV는 `<상위 경로>/<랜덤 접두사>/deletion_vector_<정식 텍스트 표현의 uuid>.bin`에 저장됩니다. 인라인 DV는 절대 경로가 없으므로 `storageType='i'`인 경우 유효한 필드가 아닙니다.

### JSON 예제 1 — 상대 경로를 사용한 디스크 저장 (랜덤 접두사 포함)
```json
{
  "storageType" : "u",
  "pathOrInlineDv" : "ab^-aqEH.-t@S}K{vb[*k^",
  "offset" : 4,
  "sizeInBytes" : 40,
  "cardinality" : 6
}
```
이 DV가 `s3://mytable/` 디렉토리에 상대적으로 저장된다고 가정하면 여기서 해결될 절대 경로는 `s3://mytable/ab/deletion_vector_d2c639aa-8816-431a-aaf6-d3fe2512ff61.bin`입니다.

### JSON 예제 2 — 절대 경로를 사용한 디스크 저장
```json
{
  "storageType" : "p",
  "pathOrInlineDv" : "s3://mytable/deletion_vector_d2c639aa-8816-431a-aaf6-d3fe2512ff61.bin",
  "offset" : 4,
  "sizeInBytes" : 40,
  "cardinality" : 6
}
```

### JSON 예제 3 — 인라인
```json
{
  "storageType" : "i",
  "pathOrInlineDv" : "wi5b=000010000siXQKl0rr91000f55c8Xg0@@D72lkbi5=-{L",
  "sizeInBytes" : 40,
  "cardinality" : 6
}
```
이 DV에 인코딩된 행 인덱스는 3, 4, 7, 11, 18, 29입니다.

## 삭제 벡터에 대한 Reader 요구사항
스냅샷에 DV로 무효화된 레코드가 있는 논리적 파일이 포함되어 있으면 이러한 레코드는 출력에 반환되어서는 *안 됩니다*.

## 삭제 벡터에 대한 Writer 요구사항
삭제 벡터가 있는 논리적 파일을 추가할 때 해당 논리적 파일은 `stats` 필드에 데이터 파일에 대한 올바른 `numRecords` 정보가 있어야 합니다.

# Iceberg 호환성 V1

이 테이블 기능(`icebergCompatV1`)은 Delta 테이블을 Apache Iceberg™ 형식으로 변환할 수 있도록 보장합니다. 그러나 이 테이블 기능은 해당 변환을 구현하거나 지정하지 않습니다.

이 기능을 지원하려면:
- 이 테이블 기능은 컬럼 매핑에 의존하므로 테이블은 Reader 버전 = 2이어야 하거나 Reader 버전 >= 3이고 `protocol`의 `readerFeatures`에 `columnMapping` 기능이 존재해야 합니다.
- 테이블은 Writer 버전 7이어야 합니다.
- 테이블 `protocol`의 `writerFeatures`에 `icebergCompatV1` 기능이 존재해야 합니다.

이 테이블 기능은 테이블 속성 `delta.enableIcebergCompatV1`이 `true`로 설정된 경우 활성화됩니다.

## IcebergCompatV1에 대한 Writer 요구사항

지원되고 활성화된 경우 Writer는 다음을 수행해야 합니다:
- 컬럼 매핑이 활성화되고 `name` 또는 `id` 모드로 설정되어야 합니다
- 삭제 벡터가 지원되지 않아야 합니다(결과적으로 활성화되지도 않음). 즉, `deletionVectors` 테이블 기능이 테이블 `protocol`에 없어야 합니다.
- 파티션 컬럼 값이 테이블에 있는 모든 Parquet 데이터 파일에 구체화되어야 하며 parquet 스키마에서 데이터 컬럼 *뒤에* 배치되어야 합니다
- 테이블에 커밋된 모든 `AddFile`이 `stats` 필드에 `numRecords` 통계가 채워져 있어야 합니다
- 테이블 스키마에 `Map`/`Array`/`Void` 타입 추가를 차단합니다(따라서 쓰기도 차단)
- 파티션된 테이블을 다른 이름의 파티션 사양으로 교체하는 것을 차단합니다
    - 예: `part_a INT`로 파티션된 테이블을 파티션 사양 `part_b INT`로 교체하는 것은 차단되어야 합니다
    - 예: `part_a INT`로 파티션된 테이블을 파티션 사양 `part_a LONG`으로 교체하는 것은 허용됩니다
- [Type Widening](#type-widening) 테이블 기능이 지원되는 경우 테이블 스키마에 기록된 [Type Change Metadata](#type-change-metadata)를 기반으로 테이블에 적용된 모든 타입 변경이 [Iceberg V2](https://iceberg.apache.org/spec/#schema-evolution)에서 지원되어야 합니다.

# Iceberg 호환성 V2

이 테이블 기능(`icebergCompatV2`)은 Delta 테이블을 Apache Iceberg™ 형식으로 변환할 수 있도록 보장합니다. 그러나 이 테이블 기능은 해당 변환을 구현하거나 지정하지 않습니다.

이 기능을 지원하려면:
- 이 테이블 기능은 컬럼 매핑에 의존하므로 테이블은 Reader 버전 = 2이어야 하거나 Reader 버전 >= 3이고 `protocol`의 `readerFeatures`에 `columnMapping` 기능이 존재해야 합니다.
- 테이블은 Writer 버전 7이어야 합니다.
- 테이블 프로토콜의 `writerFeatures`에 `icebergCompatV2` 기능이 존재해야 합니다.

이 테이블 기능은 테이블 속성 `delta.enableIcebergCompatV2`가 `true`로 설정된 경우 활성화됩니다.

## IcebergCompatV2에 대한 Writer 요구사항

이 기능이 지원되고 활성화된 경우 Writer는 다음을 수행해야 합니다:
- 컬럼 매핑이 활성화되고 `name` 또는 `id` 모드로 설정되어야 합니다
- ArrayTypes의 중첩된 `element` 필드와 MapTypes의 중첩된 `key` 및 `value` 필드에 32비트 정수 식별자가 할당되어야 합니다. 이러한 식별자는 [컬럼 매핑](#컬럼-매핑)에서 사용되는 것과 고유하고 다르며 Delta 테이블 스키마의 가장 가까운 조상 [StructField](#struct-field)의 메타데이터에 저장되어야 합니다. 동일한 `StructField`에 속하는 식별자는 `Map[String, Long]`으로 구성되어 키 `parquet.field.nested.ids`와 함께 메타데이터에 저장되어야 합니다. 맵의 키는 가장 가까운 조상 StructField의 이름을 접두사로 하는 "element", "key" 또는 "value"이며 점으로 구분됩니다. 값은 식별자입니다. 중첩된 배열 또는 중첩된 맵의 필드에 대한 키는 부모의 키를 접두사로 하며 점으로 구분됩니다. [예제](#arraytype-및-maptype의-중첩-필드에-대한-식별자-저장-예제)가 아래에 제공되어 식별자가 저장되는 방법을 보여줍니다. 이러한 식별자는 parquet 파일을 쓸 때 [Parquet Thrift 사양](https://github.com/apache/parquet-format/blob/master/src/main/thrift/parquet.thrift)의 `SchemaElement` struct의 `field_id` 필드에도 작성되어야 합니다.
- IcebergCompatV1이 활성화되지 않아야 합니다. 즉, 테이블 프로토콜에 `icebergCompatV1` 테이블 기능이 없거나 테이블 속성 `delta.enableIcebergCompatV1`이 `true`로 설정되지 않아야 합니다
- 삭제 벡터가 활성화되지 않아야 합니다. 즉, 테이블 프로토콜에 `deletionVectors` 테이블 기능이 없거나 테이블 속성 `delta.enableDeletionVectors`가 `true`로 설정되지 않아야 합니다
- Parquet 데이터 파일을 쓸 때 파티션 컬럼 값이 구체화되어야 합니다
- 테이블에 커밋된 모든 새 `AddFile`이 `stats` 필드에 `numRecords` 통계가 채워져 있어야 합니다
- 타임스탬프 컬럼을 int64로 작성해야 합니다
- 테이블 스키마에 다음 허용 목록의 데이터 타입만 포함되어야 합니다: [`byte`, `short`, `integer`, `long`, `float`, `double`, `decimal`, `string`, `binary`, `boolean`, `timestamp`, `timestampNTZ`, `date`, `array`, `map`, `struct`].
- 파티션된 테이블을 다른 이름의 파티션 사양으로 교체하는 것을 차단해야 합니다
    - 예: `part_a INT`로 파티션된 테이블을 파티션 사양 `part_b INT`로 교체하는 것은 차단되어야 합니다
    - 예: `part_a INT`로 파티션된 테이블을 파티션 사양 `part_a LONG`으로 교체하는 것은 허용됩니다
- [Type Widening](#type-widening) 테이블 기능이 지원되는 경우 테이블 스키마에 기록된 [Type Change Metadata](#type-change-metadata)를 기반으로 테이블에 적용된 모든 타입 변경이 [Iceberg V2](https://iceberg.apache.org/spec/#schema-evolution)에서 지원되어야 합니다.

### ArrayType 및 MapType의 중첩 필드에 대한 식별자 저장 예제
다음은 다음 스키마를 가진 테이블의 `ArrayType`과 `MapType`의 중첩 필드에 대한 식별자를 저장하는 예입니다:
```
|-- col1: array[array[int]] 
|-- col2: map[int, array[int]]    
|-- col3: map[int, struct]
                     |-- subcol1: array[int]
```
중첩 필드의 식별자는 메타데이터에 다음과 같이 저장됩니다:
```json
[
  {
    "name": "col1",
    "type": {
      "type": "array",
      "elementType": {
        "type": "array",
        "elementType": "int"
      }
    },
    "metadata": {
      "parquet.field.nested.ids": {
        "col1.element": 100,
        "col1.element.element": 101
      }
    }
  },
  {
    "name": "col2",
    "type": {
      "type": "map",
      "keyType": "int",
      "valueType": {
        "type": "array",
        "elementType": "int"
      }
    },
    "metadata": {
      "parquet.field.nested.ids": {
        "col2.key": 102,
        "col2.value": 103,
        "col2.value.element": 104
      }
    }
  },
  {
    "name": "col3",
    "type": {
      "type": "map",
      "keyType": "int",
      "valueType": {
        "type": "struct",
        "fields": [
          {
            "name": "subcol1",
            "type": {
              "type": "array",
              "elementType": "int"
            },
            "metadata": {
              "parquet.field.nested.ids": {
                "subcol1.element": 107
              }
            }
          }
        ]
      }
    },
    "metadata": {
      "parquet.field.nested.ids": {
        "col3.key": 105,
        "col3.value": 106
      }
    }
  }
]
```

# 시간대가 없는 타임스탬프 (TimestampNtz)
이 기능은 시간대 정보 없이 타임스탬프를 지원하는 새로운 데이터 타입을 도입합니다. 예: `1970-01-01 00:00:00` 또는 `1970-01-01 00:00:00.123456`.
직렬화 방법은 [파티션 값 직렬화](#파티션-값-직렬화) 및 [스키마 직렬화 형식](#스키마-직렬화-형식) 섹션에 설명되어 있습니다.

이 기능을 지원하려면:
- 테이블에 TimestampNtz 타입의 컬럼을 가지려면 테이블에 Reader 버전 3과 Writer 버전 7이 있어야 합니다. 테이블의 `readerFeatures` 및 `writerFeatures`에 `timestampNtz` 기능 이름이 존재해야 합니다.


# V2 체크포인트 테이블 기능
이 기능을 지원하려면:
- 테이블에 [V2 체크포인트](#v2-사양) 지원을 추가하려면 테이블에 Reader 버전 3과 Writer 버전 7이 있어야 합니다. 테이블의 `readerFeatures` 및 `writerFeatures`에 `v2Checkpoint` 기능 이름이 존재해야 합니다.

지원되는 경우:
- 테이블은 [체크포인트 메타데이터](#체크포인트-메타데이터)가 있어야 하고 [사이드카 파일](#사이드카-파일)이 있을 수 있는 [uuid 명명](#uuid-명명-체크포인트) [V2 사양 체크포인트](#v2-사양)를 사용할 수 있습니다 또는
- 테이블은 [V1](#v1-사양) 또는 [V2](#v2-사양) 사양을 따를 수 있는 [클래식](#클래식-체크포인트) 체크포인트를 사용할 수 있습니다.
- 테이블은 [다중 파트 체크포인트](#다중-파트-체크포인트)를 사용해서는 안 됩니다

# 행 추적

행 추적은 Delta 테이블의 여러 버전에 걸쳐 행을 추적할 수 있는 기능입니다.
두 개의 메타데이터 컬럼을 노출하여 이를 가능하게 합니다: 테이블의 여러 버전에 걸쳐 행을 고유하게 식별하는 행 ID와 두 개의 다른 테이블 버전에서 동일한 ID를 가진 두 행이 행의 동일한 버전을 나타내는지 확인할 수 있게 하는 행 커밋 버전입니다.

행 추적은 테이블에서 다음과 같이 **지원** 또는 **활성화**되는 것으로 정의됩니다:
- 테이블 `protocol`의 `writerFeatures`에 `rowTracking` 기능이 존재하면 행 추적이 **지원**된다고 말합니다.
  이 상황에서 Writer는 `delta.rowTrackingSuspended` 테이블 속성이 없거나 false로 설정되어 있는 한 행 ID와 커밋 버전을 할당해야 합니다. 그러나 아직 테이블에 존재한다고 의존할 수는 없습니다.
  행 추적이 지원되지만 아직 활성화되지 않은 경우 Writer는 행 ID와 커밋 버전을 보존할 수 없습니다.
- 추가로 테이블 속성 `delta.enableRowTracking`이 `true`로 설정되면 행 추적이 **활성화**되었다고 말합니다.
  이 상황에서 행 ID와 행 커밋 버전은 모든 행에 대해 테이블에 존재한다고 의존할 수 있습니다.
  행 추적이 활성화되면 Writer는 행 ID와 커밋 버전을 보존해야 합니다.
- 테이블 속성 `delta.rowTrackingSuspended`가 true로 설정되면 Writer는 행 ID와 커밋 버전 할당을 일시 중단해야 합니다.
  테이블 속성 `delta.rowTrackingSuspended`는 테이블 속성 `delta.enableRowTracking`과 함께 활성화되어서는 안 됩니다.

활성화:
- 테이블은 Writer 버전 7이어야 합니다.
- 테이블 `protocol`의 `writerFeatures`에 `rowTracking` 기능이 존재해야 합니다. 테이블 `protocol`의 `writerFeatures`에 `domainMetadata` 기능이 필요합니다.
- 테이블 속성 `delta.enableRowTracking`이 `true`로 설정되어야 합니다.
- 테이블 속성 `delta.rowTrackingSuspended`는 없거나 `false`로 설정되어야 합니다.

## 행 ID

Delta는 행 ID를 제공합니다. 행 ID는 테이블 내에서 행을 고유하게 식별하는 데 사용되는 정수입니다.
모든 행에는 두 개의 행 ID가 있습니다:

- **새로운** 또는 불안정한 **행 ID**.
  이 ID는 테이블의 한 버전 내에서 행을 고유하게 식별합니다.
  행의 새로운 ID는 수정되지 않은 행의 경우에도 테이블이 업데이트될 때마다 변경될 수 있습니다. 예를 들어 업데이트 작업 중에 행이 변경되지 않고 복사되면 새로운 새 ID를 받습니다. 새 ID는 테이블의 한 버전 내에서 행을 식별하는 데 사용할 수 있습니다. 예를 들어 셀프 조인에서 일치하는 행을 식별하는 데 사용됩니다.
- **안정적인 행 ID**.
  이 ID는 테이블 버전과 업데이트에 걸쳐 행을 고유하게 식별합니다.
  행이 삽입되면 새 ID와 동일한 새로운 안정적인 행 ID가 할당됩니다.
  행이 업데이트되거나 복사되면 이 행의 안정적인 행 ID가 보존됩니다.
  행이 복원되면(즉, 테이블이 이전 버전으로 복원되면) 안정적인 행 ID도 복원됩니다.

새 행 ID와 안정적인 행 ID가 동일할 필요는 없습니다.

행 ID는 두 가지 방식으로 저장됩니다:

- **기본 생성 행 ID**는 `add` 및 `remove` 액션에 저장된 `baseRowId` 필드를 사용하여 새 행 ID를 생성합니다.
  데이터 파일의 기본 생성 행 ID는 행이 포함된 파일의 `baseRowId`에 파일 내 행의 (물리적) 위치(인덱스)를 추가하여 계산됩니다.
  기본 생성 행 ID는 저장 오버헤드가 거의 없지만 행이 업데이트되거나 다른 파일로 이동될 때마다 재할당됩니다(예: OPTIMIZE로 압축된 파일에 행이 포함된 경우).

- **구체화된 행 ID**는 데이터 파일의 컬럼에 저장됩니다.
  이 컬럼은 Reader와 Writer에게 숨겨져 있습니다. 즉, 테이블의 `metaData`의 `schemaString`의 일부가 아닙니다.
  대신 이 컬럼의 이름은 테이블의 `metaData` 액션의 `configuration`에서 `delta.rowTracking.materializedRowIdColumnName` 키의 값에서 찾을 수 있습니다.
  이 컬럼에는 해당 행에 구체화된 행 ID가 없음을 의미하는 `null` 값이 포함될 수 있습니다. 파일에서 모든 값이 `null`인 경우 이 컬럼은 생략될 수 있습니다.
  구체화된 행 ID는 Writer가 업데이트되거나 복사된 행에 대한 안정적인 행 ID를 보존하는 메커니즘을 제공합니다.

행의 새 행 ID는 기본 생성 행 ID와 같습니다. 행의 안정적인 행 ID는 해당 컬럼이 있고 값이 NULL이 아닌 경우 행의 구체화된 행 ID와 같고, 그렇지 않으면 기본 생성 행 ID와 같습니다.

행 추적이 활성화된 경우:
- 기본 생성 행 ID는 모든 기존 행에 할당되어야 합니다.
  이는 특히 테이블 속성 `delta.enableRowTracking`을 `true`로 설정하는 테이블 버전의 일부인 모든 파일에 `baseRowId`가 설정되어야 함을 의미합니다.
  테이블 속성 `delta.enableRowTracking`을 `true`로 설정하기 전에 모든 데이터 파일에 대해 `baseRowId` 필드가 설정된 `add` 및 `remove` 액션을 커밋하는 백필 작업이 필요할 수 있습니다.

## 행 커밋 버전

행 커밋 버전은 행의 버전 관리를 제공합니다.

- **새로운** 또는 불안정한 **행 커밋 버전**은 행이 포함된 `add` 액션이 커밋된 첫 번째 커밋 버전을 식별하는 데 사용할 수 있습니다.
  행의 새 커밋 버전은 수정되지 않은 행의 경우에도 테이블이 업데이트될 때마다 변경될 수 있습니다. 예를 들어 업데이트 작업 중에 행이 변경되지 않고 복사되면 새로운 새 커밋 버전을 받습니다.
- **안정적인 행 커밋 버전**은 행(동일한 ID를 가진)이 마지막으로 삽입되거나 업데이트된 커밋 버전을 식별합니다.
  행이 삽입되거나 업데이트되면 새 행이 있는 `add` 엔트리를 포함하는 로그 엔트리의 커밋 버전 번호가 할당됩니다.
  행이 복사되면 이 행의 안정적인 행 커밋 버전이 보존됩니다.
  행이 복원되면(즉, 테이블이 이전 버전으로 복원되면) 안정적인 행 커밋 버전도 복원됩니다.

새 행 커밋 버전과 안정적인 행 커밋 버전이 동일할 필요는 없습니다.

커밋 버전은 두 가지 방식으로 저장됩니다:

- **기본 생성 행 커밋 버전**은 `add` 및 `remove` 액션의 `defaultRowCommitVersion` 필드를 사용합니다.
  기본 생성 행 커밋 버전은 저장 오버헤드가 거의 없지만 행이 업데이트되거나 다른 파일로 이동될 때마다 재할당됩니다(예: OPTIMIZE로 압축된 파일에 행이 포함된 경우).

- **구체화된 행 커밋 버전**은 데이터 파일의 컬럼에 저장됩니다.
  이 컬럼은 Reader와 Writer에게 숨겨져 있습니다. 즉, 테이블의 `metaData`의 `schemaString`의 일부가 아닙니다.
  대신 이 컬럼의 이름은 테이블의 `metaData` 액션의 `configuration`에서 `delta.rowTracking.materializedRowCommitVersionColumnName` 키의 값에서 찾을 수 있습니다.
  이 컬럼에는 해당 행에 구체화된 행 커밋 버전이 없음을 의미하는 `null` 값이 포함될 수 있습니다. 파일에서 모든 값이 `null`인 경우 이 컬럼은 생략될 수 있습니다.
  구체화된 행 커밋 버전은 Writer가 복사된 행에 대한 행 커밋 버전을 보존하는 메커니즘을 제공합니다.

행의 새 행 커밋 버전은 기본 생성 행 커밋 버전과 같습니다.
행의 안정적인 행 커밋 버전은 해당 컬럼이 있고 값이 NULL이 아닌 경우 행의 구체화된 행 커밋 버전과 같고, 그렇지 않으면 기본 생성 커밋 버전과 같습니다.

## 행 추적에 대한 Reader 요구사항

행 추적이 활성화된 경우(테이블 속성 `delta.enableRowTracking`이 `true`로 설정된 경우):
- 행 ID가 요청되면 Reader는 다음과 같이 안정적인 행 ID를 재구성해야 합니다:
    1. `delta.rowTracking.materializedRowIdColumnName`으로 결정된 컬럼이 데이터 파일에 있고 컬럼에 행에 대한 `null`이 아닌 값이 포함되어 있으면 Reader는 구체화된 행 ID를 사용해야 합니다.
    2. 그렇지 않으면 Reader는 다른 모든 경우에 행을 포함하는 `add` 또는 `remove` 액션의 기본 생성 행 ID를 사용해야 합니다.
       즉, Reader는 행을 포함하는 파일의 `add` 또는 `remove` 액션의 `baseRowId`에 파일의 행 인덱스를 추가해야 합니다.
- 행 커밋 버전이 요청되면 Reader는 다음과 같이 재구성해야 합니다:
    1. `delta.rowTracking.materializedRowCommitVersionColumnName`으로 결정된 컬럼이 데이터 파일에 있고 컬럼에 행에 대한 `null`이 아닌 값이 포함되어 있으면 Reader는 구체화된 행 커밋 버전을 사용해야 합니다.
    2. 그렇지 않으면 Reader는 다른 모든 경우에 행을 포함하는 `add` 또는 `remove` 액션의 기본 생성 행 커밋 버전을 사용해야 합니다.
       즉, Reader는 행을 포함하는 파일의 `add` 또는 `remove` 액션의 `defaultRowCommitVersion`을 사용해야 합니다.
- Reader는 `cdc` 액션에서 변경 데이터 파일을 읽는 동안 행 ID와 행 커밋 버전을 읽을 수 없습니다.

## 행 추적에 대한 Writer 요구사항

행 추적이 지원되고(테이블의 `protocol` 액션의 `writerFeatures` 필드에 `rowTracking`이 포함된 경우) 행 추적이 일시 중단되지 않은 경우(`delta.rowTrackingSuspended` 테이블 속성이 없거나 false로 설정된 경우):
- Writer는 커밋하는 모든 행에 고유한 새 행 ID를 할당해야 합니다.
    - Writer는 커밋하는 모든 `add` 액션에서 `baseRowId` 필드를 설정하여 모든 기본 생성 행 ID가 테이블 버전에서 고유하도록 해야 합니다.
      Writer는 모든 버전에서 테이블에 중복 행 ID를 커밋해서는 안 됩니다.
    - Writer는 재커밋되고 체크포인트된 `add` 액션과 `remove` 액션에서 `baseRowId` 필드를 동일한 `path`를 가진 마지막 커밋된 `add` 액션의 `baseRowId` 값(있는 경우)으로 설정해야 합니다.
    - Writer는 높은 워터마크, 즉 할당된 가장 높은 새 행 ID를 추적해야 합니다.
        - 높은 워터마크는 `delta.rowTracking`을 `domain`으로 하고 `rowIdHighWaterMark`를 키로 하고 할당된 가장 높은 새 행 ID를 값으로 하는 단일 키-값 쌍을 포함하는 `configuration`을 가진 `domainMetadata` 액션에 저장되어야 합니다.
        - Writer는 `delta.rowTracking`의 현재 `domainMetadata`의 `rowIdHighWaterMark` 값보다 높은 새로운 새 행 ID를 할당할 때마다 `delta.rowTracking`에 대한 `domainMetadata`를 포함해야 합니다.
          이 `domainMetadata` 액션의 `configuration`에서 `rowIdHighWaterMark` 값은 항상 지금까지 커밋된 가장 높은 새 행 ID보다 크거나 같아야 합니다.
          Writer는 이 `domainMetadata`를 동일한 커밋에 커밋하거나 이전 커밋에서 새 행 ID를 예약할 수 있습니다.
        - Writer는 `baseRowId` 필드를 행 ID 높은 워터마크보다 높은 값으로 설정해야 합니다.
- Writer는 커밋하는 모든 행에 새 행 커밋 버전을 할당해야 합니다.
    - Writer는 새 `add` 액션에서 `defaultRowCommitVersion` 필드를 `add` 액션을 포함하는 로그 엔트리의 버전 번호로 설정해야 합니다.
    - Writer는 재커밋되고 체크포인트된 `add` 액션과 `remove` 액션에서 `defaultRowCommitVersion` 필드를 동일한 `path`를 가진 마지막 커밋된 `add` 액션의 `defaultRowCommitVersion`으로 설정해야 합니다.

반면에 행 추적이 지원되지만 일시 중단된 경우(테이블 속성 `delta.rowTrackingSuspended`가 `true`로 설정된 경우) Writer는 `baseRowId` 또는 `defaultRowCommitVersion`을 할당해서는 안 됩니다.

Writer는 테이블의 `metaData`의 `configuration`에서 `delta.enableRowTracking`을 `true`로 설정하여 행 추적을 활성화할 수 있습니다.
이는 다음 요구 사항이 충족되는 경우에만 허용됩니다:
- `rowTracking` 기능이 테이블의 동일한 버전 또는 이전 버전에서 테이블의 `protocol` 액션의 `writerFeatures` 필드에 추가되었습니다.
- 구체화된 행 ID 및 행 커밋 버전의 컬럼 이름이 할당되고 `delta.rowTracking.materializedRowIdColumnName` 및 `delta.rowTracking.materializedRowCommitVersionColumnName` 키를 사용하여 테이블의 `metaData` 액션의 `configuration`에 추가되었습니다.
    - 할당된 컬럼 이름은 고유해야 합니다. 테이블 스키마의 다른 컬럼 이름과 같아서는 안 됩니다.
      할당된 컬럼 이름은 테이블의 모든 향후 버전에서 고유하게 유지되어야 합니다.
      [컬럼 매핑](#컬럼-매핑)이 활성화된 경우 할당된 컬럼 이름은 테이블의 물리적 컬럼 이름과 구별되어야 합니다.
- `delta.enableRowTracking`이 `true`로 설정된 테이블 버전의 모든 활성 `add` 액션에 대해 `baseRowId` 및 `defaultRowCommitVersion` 필드가 설정되어 있습니다.
- 테이블의 일부 활성 `add` 액션에서 `baseRowId` 및 `defaultRowCommitVersion` 필드가 설정되지 않은 경우 Writer는 먼저 이러한 필드가 설정되지 않은 `add` 액션을 교체하기 위해 이러한 필드를 설정하는 새 `add` 액션을 커밋해야 합니다.
  이는 `delta.enableRowTracking`을 `true`로 설정하는 커밋 또는 이전 커밋에서 수행될 수 있습니다.
  할당된 `baseRowId` 및 `defaultRowCommitVersion` 값은 각각 새 행 ID 및 새 행 커밋 버전을 할당할 때와 동일한 요구 사항을 충족해야 합니다.
  또한 Writer는 행 추적을 활성화하기 전에 테이블 속성 `delta.rowTrackingSuspended`가 없거나 false로 설정되어 있는지 확인해야 합니다.

행 추적이 활성화된 경우(테이블 속성 `delta.enableRowTracking`이 `true`로 설정된 경우):
- Writer는 모든 행에 안정적인 행 ID를 할당해야 합니다.
    - 안정적인 행 ID는 테이블 버전 내에서 고유해야 하며 동일한 테이블 버전의 다른 행의 새 행 ID와 같아서는 안 됩니다.
    - Writer는 구체화된 행 ID를 사용하여 업데이트되거나 복사된 행의 안정적인 행 ID를 보존해야 합니다.
        - 보존된 안정적인 행 ID(즉, 동일한 물리적 행의 새 행 ID와 같지 않은 안정적인 행 ID)는 업데이트되거나 복사되기 전 동일한 논리적 행의 안정적인 행 ID와 같아야 합니다.
        - 구체화된 행 ID는 테이블의 `metaData` 액션의 `configuration`에서 `delta.rowTracking.materializedRowIdColumnName`으로 결정된 컬럼에 작성되어야 합니다.
          이 컬럼의 값은 보존되지 않은 안정적인 행 ID에 대해 `NULL`로 설정되어야 합니다.
- Writer는 모든 행에 안정적인 행 커밋 버전을 할당해야 합니다.
    - Writer는 구체화된 행 커밋 버전을 사용하여 복사된(업데이트되지 않은) 행의 안정적인 행 커밋 버전을 보존해야 합니다.
        - 보존된 안정적인 행 커밋 버전(즉, 동일한 물리적 행의 새 행 커밋 버전과 같지 않은 안정적인 행 커밋 버전)은 복사되기 전 동일한 논리적 행의 안정적인 커밋 버전과 같아야 합니다.
        - 구체화된 행 커밋 버전은 테이블의 `metaData` 액션의 `configuration`에서 `delta.rowTracking.materializedRowCommitVersionColumnName`으로 결정된 컬럼에 작성되어야 합니다.
          이 컬럼의 값은 보존되지 않은(즉, 새 행 커밋 버전과 같은) 안정적인 행 커밋 버전에 대해 `NULL`로 설정되어야 합니다.
- Writer는 업데이트되거나 복사된 행의 모든 안정적인 행 ID와 복사된 행의 모든 안정적인 행 커밋 버전이 보존될 때마다 `commitInfo` 액션의 `tags`에 `delta.rowTracking.preserved`를 `true`로 설정해야 합니다.
  특히 Writer는 행이 업데이트되거나 복사되지 않은 경우 `commitInfo` 액션의 `tags`에 `delta.rowTracking.preserved`를 `true`로 설정해야 합니다.
  그렇지 않으면 Writer는 해당 플래그를 false로 설정해야 합니다.

# VACUUM 프로토콜 체크

`vacuumProtocolCheck` ReaderWriter 기능은 `VACUUM` 작업 중 Reader 및 Writer 프로토콜 체크의 일관된 적용을 보장하여 잠재적인 프로토콜 불일치를 해결하고 건너뛴 Writer 체크로 인한 데이터 손상 위험을 완화합니다.

활성화:
- 테이블은 Writer 버전 7과 Reader 버전 3이어야 합니다.
- 테이블 `protocol`의 `writerFeatures` 및 `readerFeatures`에 `vacuumProtocolCheck` 기능이 존재해야 합니다.

## Vacuum 프로토콜 체크에 대한 Writer 요구사항

이 기능은 VACUUM 작업에만 영향을 미칩니다. 표준 커밋은 영향을 받지 않습니다.

VACUUM 작업을 수행하기 전에 Writer는 테이블의 쓰기 프로토콜을 확인해야 합니다. 이는 모든 테이블에 대해 무조건적인 쓰기 프로토콜 체크를 추가하여 가장 쉽게 구현할 수 있으며, 개별 테이블 속성을 검사할 필요가 없습니다.

VACUUM을 구현하지 않는 Writer는 아무것도 변경할 필요가 없으며 기능을 활성화한 테이블에 안전하게 쓸 수 있습니다.

## Vacuum 프로토콜 체크에 대한 Reader 요구사항

Vacuum 프로토콜 체크가 활성화된 테이블의 경우 Reader는 새로운 것을 이해하거나 변경할 필요가 없습니다. 기능이 존재한다는 것을 인정하기만 하면 됩니다.

이 기능을 ReaderWriter 기능으로 만드는 것은(Writer 기능만이 아닌) 다음을 보장합니다:
- Reader 프로토콜 체크만 수행하고 Writer 프로토콜 체크가 없는 이전 vacuum 구현은 테이블에 `vacuumProtocolCheck`가 활성화되어 있으면 실패하기 시작합니다. 이 변경을 통해 향후 Writer 기능이 테이블 디렉토리 내의 파일을 관리하는 데 더 큰 유연성과 안전성을 가질 수 있으며, Writer 프로토콜 체크가 없는 이전 Vacuum 구현이 관련 파일을 실수로 삭제할 위험을 제거합니다.

# 클러스터 테이블

클러스터 테이블 기능은 미리 정의된 클러스터링 컬럼 집합에서 유사한 값을 공유하는 행의 물리적 클러스터링을 용이하게 합니다.
이는 이러한 클러스터링 컬럼에 선택적 필터가 적용될 때 데이터 건너뛰기를 통해 쿼리 성능을 향상시킵니다.
클러스터링 컬럼은 테이블의 초기 생성 중에 지정하거나 테이블에 파티션 컬럼이 없는 경우 나중에 추가할 수 있습니다.

테이블은 다음 기준을 통해 클러스터 테이블로 정의됩니다:
- 테이블 `protocol`의 `writerFeatures`에 `clustering` 기능이 존재하면 테이블이 클러스터 테이블이라고 말합니다.
  테이블 `protocol`의 `writerFeatures`에 `domainMetadata` 기능이 필요합니다.

활성화:
- 테이블은 Writer 버전 7이어야 합니다.
- 테이블 `protocol`의 `writerFeatures`에 `clustering` 기능이 생성 중 또는 나중 단계에서 존재해야 하며, 테이블에 파티션 컬럼이 없어야 합니다.

## 클러스터 테이블에 대한 Writer 요구사항

클러스터 테이블이 지원되는 경우(테이블의 `protocol` 액션의 `writerFeatures` 필드에 `clustering`이 포함된 경우):
- Writer는 `delta.clustering`을 `domain`으로 하고 모든 클러스터링 컬럼 이름을 포함하는 `configuration`을 가진 `domainMetadata` 액션에서 클러스터링 컬럼 이름을 추적해야 합니다.
  [컬럼 매핑](#컬럼-매핑)이 활성화된 경우 물리적 컬럼 이름을 사용해야 합니다.
- Writer는 `add` 액션에서 클러스터링 컬럼에 대한 [파일별 통계](#파일별-통계) 및 컬럼별 통계를 작성해야 합니다.
  새 컬럼이 클러스터링 컬럼 목록에 포함되는 경우 모든 테이블 파일에 이러한 추가 컬럼에 대한 통계가 있어야 합니다.
- 클러스터링 구현이 파일을 클러스터링할 때 Writer는 클러스터링된 파일에 대한 `add` 액션을 추가할 때 `clusteringProvider` 필드에 클러스터링 구현의 이름을 설정해야 합니다.
    - 기본적으로 클러스터링 구현은 `clusteringProvider` 필드가 동일한 클러스터링 구현의 이름 또는 현재 클러스터링 구현에 의해 대체되는 다른 클러스터링 구현의 이름으로 설정된 파일만 재클러스터링해야 합니다. 또한 클러스터링 구현은 설정되지 않은 `clusteringProvider` 필드(즉, 클러스터링되지 않은 파일)가 있는 모든 파일을 클러스터링할 수 있습니다.
    - Writer는 특정 순간에 특정 파일을 클러스터링할 필요가 없습니다.
    - 클러스터링 구현은 메타데이터를 추적하기 위해 새로운 사용자 제어 메타데이터 도메인을 추가하는 등 추가 정보를 자유롭게 추가할 수 있습니다.
- Writer는 클러스터링된 테이블과 파티션된 테이블을 동시에 정의해서는 안 됩니다.

다음은 컬럼 매핑을 활용하는 테이블의 `domainMetadata` 액션 정의 예입니다.
```json
{
  "domainMetadata": {
    "domain": "delta.clustering",
    "configuration": "{\"clusteringColumns\":[\"col-daadafd7-7c20-4697-98f8-bff70199b1f9\", \"col-5abe0e80-cf57-47ac-9ffc-a861a3d1077e\"]}",
    "removed": false
  }
}
```
위의 예는 `configuration` 필드를 이스케이프 문자를 포함하여 JSON 형식으로 변환합니다. 더 나은 이해를 위해 일반 JSON으로 표현하면 다음과 같습니다.
```json
{
  "clusteringColumns": [
    "col-daadafd7-7c20-4697-98f8-bff70199b1f9",
    "col-5abe0e80-cf57-47ac-9ffc-a861a3d1077e"
  ]
}
```


# Variant 데이터 타입

이 기능은 반구조화 데이터를 저장하는 `variant` 데이터 타입에 대한 지원을 활성화합니다.
스키마 직렬화 방법은 [스키마 직렬화 형식](#스키마-직렬화-형식)에 설명되어 있습니다.

이 기능을 지원하려면:
- 테이블은 Reader 버전 3과 Writer 버전 7이어야 합니다
- 테이블 `protocol`의 `readerFeatures` 및 `writerFeatures`에 `variantType` 기능이 존재해야 합니다.

## Variant 타입이 있는 JSON 인코딩 Delta 테이블 스키마 예제

```
{
  "type" : "struct",
  "fields" : [ {
    "name" : "raw_data",
    "type" : "variant",
    "nullable" : true,
    "metadata" : { }
  }, {
    "name" : "variant_array",
    "type" : {
      "type" : "array",
      "elementType" : {
        "type" : "variant"
      },
      "containsNull" : false
    },
    "nullable" : false,
    "metadata" : { }
  } ]
}
```

## Parquet의 Variant 데이터

Variant 데이터 타입은 [Spark Variant 바이너리 인코딩 사양](https://github.com/apache/spark/blob/master/common/variant/README.md)에 따라 두 개의 바이너리 인코딩 값으로 표현됩니다.
두 바이너리 값의 이름은 `value`와 `metadata`입니다.

Variant 데이터를 parquet 파일에 쓸 때 Variant 데이터는 다음 필드가 있는 단일 Parquet struct로 작성됩니다:

Struct 필드 이름 | Parquet 원시 타입 | 설명
-|-|-
value | binary | [Variant 바이너리 인코딩](https://github.com/apache/spark/blob/master/common/variant/README.md)에 설명된 바이너리 인코딩 Variant 값
metadata | binary | [Variant 바이너리 인코딩](https://github.com/apache/spark/blob/master/common/variant/README.md)에 설명된 바이너리 인코딩 Variant 메타데이터

parquet struct에는 두 개의 struct 필드 `value`와 `metadata`가 포함되어야 합니다.
지원되는 Writer는 두 개의 바이너리 필드를 작성해야 하며 지원되는 Reader는 두 개의 바이너리 필드를 읽어야 합니다.

[Variant shredding](https://github.com/apache/parquet-format/blob/master/VariantShredding.md)은 별도의 `variantShredding` 테이블 기능으로 나중에 도입될 예정입니다.

## Variant 데이터 타입에 대한 Writer 요구사항

Variant 타입이 지원되는 경우(테이블의 `protocol` 액션의 `writerFeatures` 필드에 `variantType`이 포함된 경우) Writer는:
- `variant` 타입의 컬럼을 [Variant 바이너리 인코딩 사양](https://github.com/apache/spark/blob/master/common/variant/README.md)을 준수하는 값을 저장하는 `value` 및 `metadata` 필드를 포함하는 struct로 parquet에 작성해야 합니다
- [Variant shredding](https://github.com/apache/parquet-format/blob/master/VariantShredding.md)에서 동일한 이름으로 필요한 필드와의 혼동을 피하기 위해 `typed_value`라는 parquet struct 필드를 작성해서는 안 됩니다.

## Variant 데이터 타입에 대한 Reader 요구사항

Variant 타입이 지원되는 경우(테이블의 `protocol` 액션의 `readerFeatures` 필드에 `variantType`이 포함된 경우) Reader는:
- Delta 스키마에서 `variant` 데이터 타입을 인식하고 허용해야 합니다
- 파일에서 Variant 데이터 타입을 읽을 때 올바른 물리적 스키마(`value` 및 `metadata` 필드가 있는 struct-of-binary)를 사용해야 합니다
- 엔진에서 컬럼을 사용할 수 있도록 해야 합니다:
    - [권장] [Spark Variant 바이너리 인코딩 사양](https://github.com/apache/spark/blob/master/common/variant/README.md)에 따라 struct-of-binary를 단일 Variant 필드로 노출하고 해석합니다.
    - [대안] 원시 물리적 struct-of-binary를 노출합니다. 예: 엔진이 Variant를 지원하지 않는 경우.
    - [대안] struct-of-binary를 문자열로 변환하고 문자열 표현을 노출합니다. 예: 엔진이 Variant를 지원하지 않는 경우.

## 다른 Delta 기능과의 호환성

기능 | Variant 데이터 타입 지원
-|-
파티션 컬럼 | **지원됨:** Variant 컬럼은 파티션된 테이블의 비파티션 컬럼이 될 수 있습니다. <br/> **지원되지 않음:** Variant는 비교 가능한 데이터 타입이 아니므로 파티션 컬럼에 포함될 수 없습니다.
클러스터 테이블 | **지원됨:** Variant 컬럼은 클러스터 테이블의 비클러스터링 컬럼이 될 수 있습니다. <br/> **지원되지 않음:** Variant는 비교 가능한 데이터 타입이 아니므로 클러스터링 컬럼에 포함될 수 없습니다.
Delta 컬럼 통계 | **지원됨:** Variant 컬럼은 `nullCount` 통계를 지원합니다. <br/> **지원되지 않음:** Variant는 비교 가능한 데이터 타입이 아니므로 Variant 컬럼은 `minValues` 및 `maxValues` 통계를 지원하지 않습니다.
생성된 컬럼 | **지원됨:** Variant 컬럼은 Variant 타입이 생성된 컬럼 표현식의 결과 타입이 아닌 한 생성된 컬럼 표현식의 소스로 사용될 수 있습니다. <br/> **지원되지 않음:** Variant 데이터 타입은 생성된 컬럼 표현식의 결과 타입이 될 수 없습니다.
Delta CHECK 제약 조건 | **지원됨:** Variant 컬럼은 CHECK 제약 조건 표현식에 사용될 수 있습니다.
기본 컬럼 값 | **지원됨:** Variant 컬럼은 기본 컬럼 값을 가질 수 있습니다.
Change Data Feed | **지원됨:** Variant 데이터 타입을 사용하는 테이블은 Delta Change Data Feed를 활성화할 수 있습니다.

# In-Commit Timestamps

In-Commit Timestamps Writer 기능은 각 커밋의 메타데이터에 단조 증가하는 타임스탬프를 저장하여 각 커밋과 강하게 연결합니다.

활성화:
- 테이블은 Writer 버전 7이어야 합니다.
- 테이블 `protocol`의 `writerFeatures`에 `inCommitTimestamp` 기능이 존재해야 합니다.
- 테이블 속성 `delta.enableInCommitTimestamps`가 `true`로 설정되어야 합니다.

## In-Commit Timestamps에 대한 Writer 요구사항

In-Commit Timestamps가 활성화된 경우:
1. Writer는 커밋에 `commitInfo`([커밋 출처 정보](#커밋-출처-정보) 참조) 액션을 작성해야 합니다.
2. `commitInfo` 액션은 커밋의 첫 번째 액션이어야 합니다.
3. `commitInfo` 액션에는 `long` 타입([원시 타입](#원시-타입) 참조)의 `inCommitTimestamp`라는 필드가 포함되어야 하며, 이는 커밋이 성공한 것으로 간주되는 시간(Unix epoch 이후 밀리초)을 나타냅니다. 이는 다음 두 값 중 큰 값입니다:
    - Writer가 커밋을 시도한 Unix epoch 이후 밀리초 단위의 시간
    - 이전 커밋의 `inCommitTimestamp`보다 1밀리초 늦은 시간
4. 이 기능이 활성화되지 않은 기간의 커밋이 있는 경우 이 기능이 활성화된 시점에 대한 출처 정보를 테이블 속성에서 추적해야 합니다:
    - 속성 `delta.inCommitTimestampEnablementVersion`을 사용하여 이 기능이 활성화된 테이블 버전을 추적해야 합니다.
    - 속성 `delta.inCommitTimestampEnablementTimestamp`는 이 기능이 활성화된 커밋의 `inCommitTimestamp`와 동일해야 합니다.
5. 이 기능을 활성화하는 커밋의 `inCommitTimestamp`는 바로 이전 커밋의 파일 수정 시간보다 커야 합니다.

## In-Commit Timestamps가 있는 테이블의 Reader에 대한 권장사항

In-Commit timestamps가 활성화된 테이블의 경우 Reader는 시간 여행 및 [`DESCRIBE HISTORY`](https://docs.delta.io/latest/delta-utility.html#retrieve-delta-table-history)와 같은 작업에 대한 커밋 타임스탬프로 `inCommitTimestamp`를 사용해야 합니다.
In-Commit timestamps가 활성화되기 전 기간의 커밋이 있는 테이블의 경우 테이블 속성 `delta.inCommitTimestampEnablementVersion` 및 `delta.inCommitTimestampEnablementTimestamp`가 설정되어 `inCommitTimestamp`가 없는 커밋을 식별하는 데 사용할 수 있습니다.
이러한 테이블의 커밋 타임스탬프를 올바르게 확인하려면 Reader는 다음 규칙을 사용할 수 있습니다:
1. 버전 >= `delta.inCommitTimestampEnablementVersion`인 커밋의 경우 Reader는 `commitInfo` 액션의 `inCommitTimestamp` 필드를 사용해야 합니다.
2. 버전 < `delta.inCommitTimestampEnablementVersion`인 커밋의 경우 Reader는 파일 수정 타임스탬프를 사용해야 합니다.

또한 `타임스탬프 X`를 기준으로 테이블 상태를 가져와야 하는 타임스탬프 기반 시간 여행을 시도할 때 Reader는 다음 규칙을 사용해야 합니다:
1. `타임스탬프 X` >= `delta.inCommitTimestampEnablementTimestamp`인 경우 쿼리에 대해 테이블 버전 >= `delta.inCommitTimestampEnablementVersion`만 고려해야 합니다.
2. 그렇지 않으면 쿼리에 대해 `delta.inCommitTimestampEnablementVersion`보다 작은 테이블 버전만 고려해야 합니다.

# Type Widening

Type Widening 기능은 기존 Delta 테이블의 컬럼 또는 필드 타입을 더 넓은 타입으로 변경할 수 있게 합니다.

지원되는 타입 변경은 다음과 같습니다:
- 정수 확장:
    - `Byte` -> `Short` -> `Int` -> `Long`
- 부동 소수점 확장:
    - `Float` -> `Double`
    - `Byte`, `Short` 또는 `Int` -> `Double`
- Date 확장:
    - `Date` -> `Timestamp without timezone`
- Decimal 확장 - `p`와 `s`는 각각 decimal 정밀도와 스케일을 나타냅니다.
    - `Decimal(p, s)` -> `Decimal(p + k1, s + k2)` 여기서 `k1 >= k2 >= 0`.
    - `Byte`, `Short` 또는 `Int` -> `Decimal(10 + k1, k2)` 여기서 `k1 >= k2 >= 0`.
    - `Long` -> `Decimal(20 + k1, k2)` 여기서 `k1 >= k2 >= 0`.

이 기능을 지원하려면:
- 테이블은 Reader 버전 3과 Writer 버전 7이어야 합니다.
- 테이블 `protocol`의 `readerFeatures` 및 `writerFeatures`에 `typeWidening` 기능이 생성 중 또는 나중 단계에서 존재해야 합니다.

지원되는 경우:
- 테이블은 Delta 스키마에 `delta.enableTypeWidening` 메타데이터 속성이 `true`로 설정되어 있을 수 있습니다. Writer는 이 속성이 `true`로 설정되어 있지 않으면 확장 타입 변경을 거부해야 합니다.
- 테이블 스키마의 컬럼 또는 필드에 대한 `metadata`에는 해당 컬럼 또는 필드에 대한 타입 변경 히스토리를 저장하는 `delta.typeChanges` 키가 포함될 수 있습니다.

### Type Change Metadata

테이블에 적용된 타입 변경은 테이블 스키마에 기록되고 키 `delta.typeChanges`를 사용하여 가장 가까운 조상 [StructField](#struct-field)의 `metadata`에 저장됩니다.
키 `delta.typeChanges`의 값은 JSON 객체 목록이어야 하며, 각 객체에는 다음 필드가 포함됩니다:
필드 이름 | 선택/필수 | 설명
-|-|-
`fromType`| 필수 | 타입 변경 전 컬럼 또는 필드의 타입.
`toType`| 필수 | 타입 변경 후 컬럼 또는 필드의 타입.
`fieldPath`| 선택 | 맵 키/값 또는 배열 요소의 타입만 업데이트할 때: 메타데이터를 보유하는 struct 필드에서 업데이트된 맵 키/값 또는 배열 요소까지의 경로.

`fieldPath` 값은 맵 키, 맵 값, 배열 요소의 타입을 업데이트할 때 각각 "key", "value", "element"입니다.
중첩된 맵과 중첩된 배열의 `fieldPath` 값은 부모의 경로를 접두사로 하며 점으로 구분됩니다.

다음은 두 번의 타입 변경을 거친 컬럼 정의의 예입니다:
```json
{
    "name" : "e",
    "type" : "long",
    "nullable" : true,
    "metadata" : { 
      "delta.typeChanges": [
        {
          "fromType": "short",
          "toType": "integer"
        },
        {
          "fromType": "integer",
          "toType": "long"
        }
      ]
    }
  }
```

다음은 맵 키의 타입을 변경한 후 컬럼 정의의 예입니다:
```json
{
    "name" : "e",
    "type" : {
      "type": "map",
      "keyType": "double",
      "valueType": "integer",
      "valueContainsNull": true
    },
    "nullable" : true,
    "metadata" : { 
      "delta.typeChanges": [
        {
          "fromType": "float",
          "toType": "double",
          "fieldPath": "key"
        }
      ]
    }
  }
```

다음은 배열에 중첩된 맵 값의 타입을 변경한 후 컬럼 정의의 예입니다:
```json
{
    "name" : "e",
    "type" : {
      "type": "array",
      "elementType": {
        "type": "map",
        "keyType": "string",
        "valueType": "decimal(10, 4)",
        "valueContainsNull": true
      },
      "containsNull": true
    },
    "nullable" : true,
    "metadata" : { 
      "delta.typeChanges": [
        {
          "fromType": "decimal(6, 2)",
          "toType": "decimal(10, 4)",
          "fieldPath": "element.value"
        }
      ]
    }
  }
```

## Type Widening에 대한 Writer 요구사항

Type Widening이 지원되는 경우(테이블의 `protocol` 액션의 `writerFeatures` 필드에 `typeWidening`이 포함된 경우):
- Writer는 지원되지 않는 타입 변경 적용을 거부해야 합니다.
- [Iceberg 호환성 V1](#iceberg-호환성-v1) 또는 [Iceberg 호환성 V2](#iceberg-호환성-v2) 테이블 기능이 지원되는 경우 Writer는 [Iceberg V2](https://iceberg.apache.org/spec/#schema-evolution)에서 지원하지 않는 타입 변경 적용을 거부해야 합니다:
    - `Byte`, `Short` 또는 `Int` -> `Double`
    - `Date`  -> `Timestamp without timezone`
    - Decimal 스케일 증가
    - `Byte`, `Short`, `Int` 또는 `Long` -> `Decimal`
- Writer는 가장 가까운 조상 [StructField](#struct-field)의 `metadata`에 타입 변경 정보를 기록해야 합니다. [Type Change Metadata](#type-change-metadata)를 참조하세요.
- Writer는 테이블 스키마가 업데이트될 때 스키마의 메타데이터 필드에서 `delta.typeChanges` 필드를 보존해야 합니다.
- Writer는 모든 데이터 파일이 테이블 스키마와 동일한 필드 타입을 사용하는 경우 테이블 스키마에서 `delta.typeChanges` 메타데이터를 제거할 수 있습니다.

Type Widening이 활성화된 경우(테이블 속성 `delta.enableTypeWidening`이 `true`로 설정된 경우):
- Writer는 컬럼, struct 필드, 맵 키/값 또는 배열 요소에 지원되는 타입 변경을 적용하기 위해 테이블 스키마 업데이트를 허용해야 합니다.

테이블에서 Type Widening 테이블 기능을 제거할 때, 테이블의 `protocol` 액션의 `writerFeatures` 및 `readerFeatures` 필드에서 `typeWidening`을 제거하는 버전에서:
- Writer는 테이블 스키마에 `delta.typeChanges` 메타데이터 키가 없는지 확인해야 합니다. 이를 위해서는 타입 확장 메타데이터 제거 요구 사항을 충족하기 위해 모든 데이터 파일이 테이블 스키마와 동일한 필드 타입을 사용하도록 보장하기 위해 기존 데이터 파일을 다시 작성해야 할 수 있습니다.
- Writer는 테이블 속성 `delta.enableTypeWidening`이 설정되지 않았는지 확인해야 합니다.

## Type Widening에 대한 Reader 요구사항
Type Widening이 지원되는 경우(테이블의 `protocol` 액션의 `readerFeatures` 필드에 `typeWidening`이 포함된 경우):
- Reader는 테이블이 지원되는 타입 변경을 거치기 전에 작성된 데이터 파일 읽기를 허용해야 하며 이러한 값을 현재의 더 넓은 타입으로 변환해야 합니다.
- Reader는 읽고 있는 테이블 버전의 테이블 스키마에서 `delta.typeChanges` 필드의 모든 타입 변경을 지원하는지 검증해야 하며 지원되지 않는 타입 변경이 발견되면 실패해야 합니다.

# Writer 요구사항
이 섹션에서는 Delta가 제공하는 일부 상위 수준 보장을 유지하기 위해 writer가 따라야 하는 추가 요구사항을 문서화합니다.

## 새 로그 엔트리 생성
- Writer는 기존 로그 엔트리를 절대 덮어쓰지 않아야 합니다. 가능한 경우 기본 파일 시스템의 원자적 프리미티브를 사용하여 동시 writer가 서로의 엔트리를 덮어쓰지 않도록 해야 합니다.

## 테이블 메타데이터와 데이터 파일 간의 일관성
- 테이블에 존재하는 데이터 파일에 있는 모든 컬럼은 테이블의 메타데이터에도 존재해야 합니다.
- 스키마에 있는 모든 파티션 컬럼의 값은 테이블의 모든 파일에 존재해야 합니다.
- 테이블 스키마에 있는 컬럼은 데이터 파일에서 누락될 수 있습니다. Reader는 이러한 누락된 컬럼을 `null`로 채워야 합니다.

## Delta 로그 엔트리
- 단일 로그 엔트리는 서로 조정되는 둘 이상의 액션을 포함해서는 안 됩니다.
    - 동일한 `(path, DV)` 튜플을 가진 Add / Remove 액션
    - 둘 이상의 Metadata 액션
    - 둘 이상의 protocol 액션
    - 동일한 `appId`를 가진 둘 이상의 SetTransaction

## 체크포인트
체크포인트의 각 행은 단일 액션에 해당합니다. 체크포인트는 다음 액션에 관한 모든 정보를 **반드시** 포함해야 합니다:
* [프로토콜 버전](#프로토콜-진화)
* 테이블의 [메타데이터](#메타데이터-변경)
* [추가](#파일-추가-및-파일-제거)되었고 아직 제거되지 않은 파일
* 최근 [제거](#파일-추가-및-파일-제거)되었고 아직 만료되지 않은 파일
* [트랜잭션 식별자](#트랜잭션-식별자)
* [도메인 메타데이터](#도메인-메타데이터)
* [체크포인트 메타데이터](#체크포인트-메타데이터) - [V2 체크포인트](#v2-사양) 필요
* [사이드카 파일](#사이드카-파일) - [V2 체크포인트](#v2-사양) 필요

이러한 모든 액션은 parquet의 개별 컬럼에 struct 필드로 저장됩니다. 누락된 컬럼은 null로 처리되어야 합니다.

체크포인트는 [커밋 출처 정보](#커밋-출처-정보)나 [변경 데이터](#cdc-파일-추가) 액션을 보존해서는 안 됩니다.

체크포인트 내에서 `add` struct는 테이블 구성에 따라 다음 컬럼을 포함할 수도 있고 포함하지 않을 수도 있습니다:
- partitionValues_parsed: 이 struct에서 컬럼 이름은 파티션 컬럼에 해당하며 값은 해당 데이터 타입으로 저장됩니다. 테이블이 파티션되어 있고 테이블 속성 `delta.checkpoint.writeStatsAsStruct`가 `true`로 설정된 경우 필수 필드입니다. 테이블이 파티션되어 있지 않으면 이 컬럼은 생략될 수 있습니다. 예를 들어, 데이터 타입이 각각 `int`, `int`, `string`인 파티션 컬럼 `year`, `month`, `event`의 경우 이 필드의 스키마는 다음과 같습니다:

 ```
|-- add: struct
|    |-- partitionValues_parsed: struct
|    |    |-- year: int
|    |    |-- month: int
|    |    |-- event: string
 ```

- stats: 컬럼 수준 통계는 체크포인트에 JSON 문자열로 저장될 수 있습니다. 이 필드는 통계를 사용할 수 있고 테이블 속성 `delta.checkpoint.writeStatsAsJson`이 `true`(기본값)로 설정된 경우 작성되어야 합니다. 이 속성이 `false`로 설정되면 이 필드는 체크포인트에서 생략되어야 합니다.
- stats_parsed: 통계는 [원래 형식](#파일별-통계)으로 저장될 수 있습니다. 이 필드는 통계를 사용할 수 있고 테이블 속성 `delta.checkpoint.writeStatsAsStruct`가 `true`로 설정된 경우 작성되어야 합니다. 이 속성이 `false`(기본값)로 설정되면 이 필드는 체크포인트에서 생략되어야 합니다.

체크포인트 내에서 `remove` struct는 `stats` 및 `tags` 필드를 포함하지 않습니다. 체크포인트에 저장된 `remove` 액션은 VACUUM 작업의 톰스톤 역할만 하며, VACUUM 톰스톤에는 `stats`나 `tags`가 필요하지 않기 때문입니다. 이러한 필드는 Delta JSON 커밋 파일에만 저장됩니다.

체크포인트의 스키마 예제는 [부록](#checkpoint-schema)을 참조하세요.

Delta는 두 가지 체크포인트 사양과 세 가지 체크포인트 명명 스키마를 지원합니다.

### 체크포인트 사양
Delta는 다음 두 가지 체크포인트 사양을 지원합니다:

#### V2 사양
이 체크포인트 사양은 [사이드카 파일](#사이드카-파일)에 [파일 추가 및 제거](#파일-추가-및-파일-제거)를 넣을 수 있습니다. 이 사양은 [v2 체크포인트 테이블 기능](#v2-체크포인트-테이블-기능)이 활성화된 경우에만 사용할 수 있습니다.
V2 사양을 따르는 체크포인트는 다음과 같은 구조를 가집니다:
- 각 v2 사양 체크포인트는 정확히 하나의 [체크포인트 메타데이터](#체크포인트-메타데이터) 액션을 포함합니다.
- V2 사양 체크포인트의 나머지 행은 [여기](#체크포인트-1)에 언급된 다른 액션을 참조합니다.
- 모든 비파일 액션, 즉 [파일 추가 및 제거](#파일-추가-및-파일-제거)를 제외한 모든 액션은 v2 사양 체크포인트 자체의 일부여야 합니다.
- Writer는 V2 사양 체크포인트에 [파일 추가 및 제거](#파일-추가-및-파일-제거) 액션을 포함하거나, [파일 추가 및 제거](#파일-추가-및-파일-제거) 액션을 별도의 [사이드카 파일](#사이드카-파일)에 작성할 수 있습니다. 이러한 사이드카 파일은 V2 사양 체크포인트에서 참조됩니다. 모든 사이드카 파일은 `_delta_log/_sidecars` 디렉터리에 있습니다.
- V2 사양 체크포인트는 0개 이상의 [사이드카 파일 액션](#사이드카-파일-정보)을 참조할 수 있습니다.

참고: V2 사양 체크포인트는 모든 [파일 추가 및 제거](#파일-추가-및-파일-제거) 액션을 자체 내에 포함하거나 모두 [사이드카 파일](#사이드카-파일)에 있어야 합니다. V2 체크포인트에 일부 파일 추가 및 제거 액션이 있고 사이드카 파일에 일부 항목이 있는 것은 허용되지 않습니다.

V2 사양 체크포인트를 생성한 후 writer는 reader가 V2 체크포인트를 읽을 필요가 없도록 V2 사양 체크포인트의 일부 또는 전체를 `_last_checkpoint` 파일에 포함하도록 선택할 수 있습니다.

예: V2 사양 체크포인트의 내용 표시:
```
{"checkpointMetadata":{"version":364475,"tags":{}}}
{"metaData":{...}}
{"protocol":{...}}
{"txn":{"appId":"3ba13872-2d47-4e17-86a0-21afd2a22395","version":364475}}
{"txn":{"appId":"3ae45b72-24e1-865a-a211-34987ae02f2a","version":4389}}
{"sidecar":{"path":"3a0d65cd-4056-49b8-937b-95f9e3ee90e5.parquet","sizeInBytes":2341330,"modificationTime":1512909768000,"tags":{}}
{"sidecar":{"path":"016ae953-37a9-438e-8683-9a9a4a79a395.parquet","sizeInBytes":8468120,"modificationTime":1512909848000,"tags":{}}
```

사이드카 없는 v2 사양 체크포인트의 또 다른 예:
```
{"checkpointMetadata":{"version":364475,"tags":{}}}
{"metaData":{...}}
{"protocol":{...}}
{"txn":{"appId":"3ba13872-2d47-4e17-86a0-21afd2a22395","version":364475}}
{"add":{"path":"date=2017-12-10/part-000...c000.gz.parquet",...}
{"add":{"path":"date=2017-12-09/part-000...c000.gz.parquet",...}
{"remove":{"path":"date=2017-12-08/part-000...c000.gz.parquet",...}
```

#### V1 사양

V1 사양은 [사이드카 파일](#사이드카-파일)과 [체크포인트 메타데이터](#체크포인트-메타데이터)를 지원하지 않습니다.
이는 [여기](#체크포인트-1)에 언급된 모든 액션을 포함하는 플랫 체크포인트입니다.

### 체크포인트 명명 스키마
Delta는 UUID 명명, 클래식, 다중 파트의 세 가지 체크포인트 명명 스키마를 지원합니다.

#### UUID 명명 체크포인트
이 명명 스키마는 다음 파일 이름을 가진 [V2 사양 체크포인트](#v2-사양)를 나타냅니다: `n.checkpoint.u.{json/parquet}`,
여기서 `u`는 UUID이고 `n`은 이 체크포인트가 나타내는 스냅샷 버전입니다.
UUID 명명 체크포인트는 JSON 또는 parquet 형식일 수 있습니다. [V2 사양](#v2-사양)을 따르므로 [체크포인트 메타데이터](#체크포인트-메타데이터) 액션을 가져야 하며 0개 이상의 체크포인트 [사이드카 파일](#사이드카-파일)을 참조할 수 있습니다.

예제-1: 사이드카가 있는 Json UUID 명명 체크포인트

```
00000000000000000010.checkpoint.80a083e8-7026-4e79-81be-64bd76c43a11.json
_sidecars/016ae953-37a9-438e-8683-9a9a4a79a395.parquet
_sidecars/3a0d65cd-4056-49b8-937b-95f9e3ee90e5.parquet
_sidecars/7d17ac10-5cc3-401b-bd1a-9c82dd2ea032.parquet
```

예제-2: 사이드카가 있는 Parquet UUID 명명 체크포인트

```
00000000000000000020.checkpoint.80a083e8-7026-4e79-81be-64bd76c43a11.parquet
_sidecars/016ae953-37a9-438e-8683-9a9a4a79a395.parquet
_sidecars/3a0d65cd-4056-49b8-937b-95f9e3ee90e5.parquet
```

예제-3: 사이드카 없는 Json UUID 명명 체크포인트

```
00000000000000000112.checkpoint.80a083e8-7026-4e79-81be-64bd76c43a11.json
```

#### 클래식 체크포인트

버전 `n`에 대한 클래식 체크포인트는 파일 이름 `n.checkpoint.parquet`를 사용합니다. 예를 들어:

```
00000000000000000010.checkpoint.parquet
```

두 체크포인트 writer가 동일한 클래식 체크포인트를 생성하기 위해 경쟁하면 마지막 writer가 이깁니다.
그러나 두 체크포인트 모두 동일한 정보를 포함해야 하므로 reader는 둘 중 하나를 안전하게 사용할 수 있으므로 문제가 되지 않습니다.

클래식 체크포인트는:
1. [V1 사양](#v1-사양)을 따르거나
2. [V2 사양](#v2-사양)을 따를 수 있습니다. 이는 [V2 체크포인트 테이블 기능](#v2-체크포인트-테이블-기능)이 활성화된 경우에만 가능합니다. 이 경우 [체크포인트 메타데이터](#체크포인트-메타데이터)를 포함해야 하며 [사이드카 파일](#사이드카-파일-정보)이 있을 수도 있고 없을 수도 있습니다.

#### 다중 파트 체크포인트
다중 파트 체크포인트는 parquet 형식을 사용합니다.
이 체크포인트 타입은 [더 이상 사용되지 않으며](#다중-파트-체크포인트의-문제점) writer는 사용을 피해야 합니다.

버전 `n`에 대한 다중 파트 체크포인트는 `p`개의 "파트" 파일(`p > 1`)로 구성되며, `p` 중 파트 `o`는 `n.checkpoint.o.p.parquet`로 명명됩니다. 예를 들어:

```
00000000000000000010.checkpoint.0000000001.0000000003.parquet
00000000000000000010.checkpoint.0000000002.0000000003.parquet
00000000000000000010.checkpoint.0000000003.0000000003.parquet
```

[안전상의 이유](#다중-파트-체크포인트의-문제점)로 다중 파트 체크포인트는 반드시 spark 스타일 해시 파티셔닝으로 클러스터링되어야 합니다. 테이블이 [삭제 벡터](#삭제-벡터)를 지원하는 경우 파티셔닝 키는 논리적 파일 식별자 `(path, dvId)`입니다. 그렇지 않으면 키는 `path`(`(path, NULL)`이 아님)입니다. 이는 파일을 작성하려는 여러 시도의 경우 각 파트 파일의 내용이 결정론적이 되도록 보장합니다 -- 이전 Delta 클라이언트와 최신 Delta 클라이언트가 경쟁하는 경우에도 마찬가지입니다.

##### 다중 파트 체크포인트의 문제점

원자적으로 작성할 수 없기 때문에 다중 파트 체크포인트에는 여러 가지 약점이 있습니다:

1. Writer는 reader가 사용을 시작하기 전에 방금 작성한 체크포인트의 내용을 검증할 수 없습니다.

2. 동일한 체크포인트(동일한 버전, 동일한 파트 수)를 생성하기 위해 경쟁하는 두 writer는 서로를 덮어써서 체크포인트 파트 파일의 임의 혼합을 생성할 수 있습니다. 덮어쓰기가 파일의 내용을 어떤 식으로든 변경하면 결과 체크포인트가 정확한 스냅샷을 생성하지 못할 수 있습니다.

3. 성능 및 확장성 최적화에 적합하지 않습니다. 예를 들어, 체크포인트 파트에 대한 건너뛰기 통계를 저장하거나 여러 체크포인트에서 체크포인트 파트 파일을 재사용할 방법이 없습니다.

4. 다중 파트 체크포인트는 _delta_log 디렉터리를 비대하게 만들고 LIST 작업을 느리게 합니다.

[UUID 명명](#uuid-명명-체크포인트) 체크포인트([V2 사양](#v2-사양) 준수)는 이러한 모든 문제를 해결하며 다중 파트 체크포인트보다 선호되어야 합니다. 이러한 이유로 [V2 체크포인트 테이블 기능](#v2-체크포인트-테이블-기능)이 활성화된 경우 다중 파트 체크포인트는 금지됩니다.

### UUID 명명 v2 체크포인트로 이동 시 하위 호환성 처리

UUID 명명 v2 체크포인트는 [v2 체크포인트 테이블 기능](#v2-체크포인트-테이블-기능)이 활성화된 경우에만 클라이언트에 의해 생성되어야 합니다.
UUID 명명 v2 체크포인트가 활성화된 경우, Writer는 [v2 체크포인트 테이블 기능](#v2-체크포인트-테이블-기능)을 지원하지 않아 UUID 명명 체크포인트를 인식하지 못하는 이전 클라이언트와의 호환성을 유지하기 위해 때때로 v2 [클래식 체크포인트](#클래식-체크포인트)를 생성해야 합니다. 이러한 클래식 체크포인트는 UUID 명명 v2 체크포인트와 동일한 내용을 가지지만, 이전 클라이언트는 클래식 파일 이름을 인식하여 [프로토콜](#프로토콜-진화)을 추출하고 v2 체크포인트 활성화 테이블에서 잘못된 프로토콜 버전 오류로 우아하게 실패할 수 있습니다. Writer는 이전 클라이언트가 이를 발견하고 우아하게 실패할 수 있도록 충분히 자주 클래식 체크포인트를 생성해야 합니다.

### 메타데이터 정리

_delta_log 디렉터리는 더 많은 커밋과 체크포인트가 누적됨에 따라 시간이 지남에 따라 커집니다.
구현은 디렉터리 크기를 줄이기 위해 만료된 커밋 및 체크포인트를 삭제하는 것이 권장됩니다.
다음 단계를 사용하여 DeltaLog 디렉터리를 정리할 수 있습니다:
1. deltaLog를 보존하려는 임계값(일)을 식별합니다. 해당 날짜의 UTC 자정을 `cutOffTimestamp`라고 합니다. `cutOffTimestamp`보다 최신이 아닌 가장 최신 커밋이 `cutoffCommit`입니다. 자정 정각의 커밋은 허용 가능한 컷오프이기 때문입니다. `cutoffCommit`을 포함하여 그 이후의 모든 것을 보존하려고 합니다.
2. `cutOffCommit`보다 최신이 아닌 가장 최신 체크포인트를 식별합니다. `cutOffCommit`에 있는 체크포인트가 이상적이지만 이전 체크포인트도 괜찮습니다. 이를 `cutOffCheckpoint`라고 합니다.
   `cutOffCheckpoint`(체크포인트 파일 및 해당 버전의 JSON 커밋 파일 모두)와 그 이후의 모든 커밋을 보존해야 합니다. `cutOffCheckpoint` 버전의 JSON 커밋 파일은 체크포인트가 [커밋 출처 정보](#커밋-출처-정보)(예: `commitInfo` 액션)를 보존하지 않기 때문에 보존되어야 하며, 이는 [커밋 내 타임스탬프](#in-commit-timestamps)와 같은 테이블 기능에 필요할 수 있습니다. `cutOffCheckpoint` 이후의 모든 커밋은 `cutOffCheckpoint`와 다음 사용 가능한 체크포인트 사이의 커밋에 대한 시간 이동을 활성화하기 위해 보존되어야 합니다.
3. `cutOffCheckpoint` 체크포인트 이전의 모든 [델타 로그 엔트리](#delta-로그-엔트리)와 [체크포인트 파일](#체크포인트)을 삭제합니다. 또한 startVersion <= `cutOffCheckpoint` 버전인 모든 [로그 압축 파일](#로그-압축-파일)을 삭제합니다.
4. 이제 _delta_log 디렉터리의 사용 가능한 모든 [체크포인트](#체크포인트-1)를 읽고 해당 [사이드카 파일](#사이드카-파일)을 식별합니다. 이러한 사이드카 파일은 보호되어야 합니다.
5. `_delta_log/_sidecars` 디렉터리의 모든 파일을 나열하고, 진행 중인 체크포인트를 중단하지 않도록 하루 미만(UTC 자정 기준)인 파일을 보존합니다. 또한 위의 4단계에서 식별된 참조된 사이드카 파일을 보존합니다. 나머지는 모두 삭제합니다.

## 데이터 파일
- 데이터 파일은 고유하게 명명되어야 하며 덮어쓰지 않아야 합니다. 참조 구현은 이 속성을 보장하기 위해 이름에 GUID를 사용합니다.

## 추가 전용 테이블
이 기능을 지원하려면:
- 테이블은 Writer 버전 2부터 7까지여야 합니다.
- 테이블이 Writer 버전 7에 있는 경우, 테이블 `protocol`의 `writerFeatures`에 기능 `appendOnly`가 존재해야 합니다.

지원되고 테이블에 `delta.appendOnly` 속성이 `true`로 설정된 경우:
- 새 로그 엔트리는 테이블에서 데이터를 변경하거나 제거해서는 안 됩니다.
- 새 로그 엔트리는 데이터를 재배열할 수 있습니다(즉, `dataChange=false`인 `add` 및 `remove` 액션).

추가 전용 제한을 제거하려면 테이블 속성 `delta.appendOnly`를 `false`로 설정하거나 제거해야 합니다.

## 컬럼 불변성
이 기능을 지원하려면
- 테이블이 Writer 버전 2부터 6까지에 있는 경우, 컬럼 불변성은 항상 활성화됩니다.
- 테이블이 Writer 버전 7에 있는 경우, 테이블 `protocol`의 `writerFeatures`에 기능 `invariants`가 존재해야 합니다.

지원되는 경우:
- 테이블 스키마의 컬럼에 대한 `metadata`는 키 `delta.invariants`를 포함할 수 있습니다.
- `delta.invariants`의 값은 `expression.expression` 키에 boolean SQL 표현식을 포함하는 JSON 문자열로 구문 분석되어야 합니다(즉, `{"expression": {"expression": "<SQL STRING>"}}`).
- Writer는 불변성이 `false` 또는 `null`로 평가되는 테이블에 행을 추가하는 트랜잭션을 중단해야 합니다.

예를 들어, 다음 스키마 문자열이 주어진 경우(가독성을 위해 예쁘게 인쇄됨. 로그의 전체 스키마 문자열은 단일 JSON 줄이어야 함):

```json
{
    "type": "struct",
    "fields": [
        {
            "name": "x",
            "type": "integer",
            "nullable": true,
            "metadata": {
                "delta.invariants": "{\"expression\": { \"expression\": \"x > 3\"} }"
            }
        }
    ]
}
```

Writer는 표현식 `x > 3`이 `false` 또는 `null`을 반환하는 데이터를 포함하는 트랜잭션을 거부해야 합니다.

## CHECK 제약 조건

이 기능을 지원하려면:
- 테이블이 Writer 버전 3부터 6까지에 있는 경우, CHECK 제약 조건은 항상 지원됩니다.
- 테이블이 Writer 버전 7에 있는 경우, 테이블 `protocol`의 `writerFeatures`에 기능 이름 `checkConstraints`가 존재해야 합니다.

CHECK 제약 조건은 [메타데이터](#메타데이터-변경)의 `configuration` 필드 맵에 저장됩니다. 각 CHECK 제약 조건에는 이름이 있으며 키 값 쌍으로 저장됩니다. 키 형식은 `delta.constraints.{name}`이고, 값은 반환 타입이 `Boolean`이어야 하는 SQL 표현식 문자열입니다. SQL 표현식이 참조하는 컬럼은 테이블 스키마에 존재해야 합니다.

테이블의 행은 CHECK 제약 조건을 만족해야 합니다. 즉, CHECK 제약 조건의 SQL 표현식을 평가하면 테이블의 각 행에 대해 `true`를 반환해야 합니다.

예를 들어, 키 값 쌍 (`delta.constraints.birthDateCheck`, `birthDate > '1900-01-01'`)은 테이블에 `birthDateCheck`라는 CHECK 제약 조건이 있고 각 행의 `birthDate` 컬럼 값이 `1900-01-01`보다 커야 함을 의미합니다.

따라서 writer는 다음 규칙을 따라야 합니다:
- 위의 "이 기능을 지원하려면" 규칙이 충족되지 않는 한 CHECK 제약 조건을 테이블에 추가할 수 없습니다. 테이블에 처음으로 CHECK 제약 조건을 추가할 때 writer는 이 기능의 지원을 추가하기 위해 동일한 커밋에서 `protocol` 변경을 제출할 수 있습니다.
- 테이블에 CHECK 제약 조건을 추가할 때 writer는 테이블의 기존 데이터를 검증하고 변경을 커밋하기 전에 모든 행이 새 CHECK 제약 조건을 만족하는지 확인해야 합니다. 그렇지 않으면 쓰기 작업이 실패하고 테이블은 변경되지 않은 상태로 유지되어야 합니다.
- CHECK 제약 조건을 포함하는 테이블에 쓰기할 때 테이블에 쓰여지는 모든 새 행은 테이블의 CHECK 제약 조건을 만족해야 합니다. 그렇지 않으면 쓰기 작업이 실패하고 테이블은 변경되지 않은 상태로 유지되어야 합니다.

## 생성된 컬럼

이 기능을 지원하려면:
- 테이블이 Writer 버전 4부터 6까지에 있는 경우, 생성된 컬럼은 항상 지원됩니다.
- 테이블이 Writer 버전 7에 있는 경우, 테이블 `protocol`의 `writerFeatures`에 기능 이름 `generatedColumns`가 존재해야 합니다.

지원되는 경우:
- 테이블 스키마의 컬럼에 대한 `metadata`는 키 `delta.generationExpression`을 포함할 수 있습니다.
- `delta.generationExpression`의 값은 SQL 표현식으로 구문 분석되어야 합니다.
- Writer는 테이블에 쓰는 모든 데이터가 `(<value> <=> <generation expression>) IS TRUE` 조건을 만족하도록 강제해야 합니다. `<=>`는 `=` 연산자처럼 동등 비교를 수행하지만 두 피연산자가 모두 `NULL`인 경우 `NULL` 대신 `TRUE`를 반환하는 NULL 안전 동등 연산자입니다.

## 기본 컬럼

Delta는 Delta 테이블의 컬럼에 대한 기본 표현식 정의를 지원합니다. Delta는 사용자가 테이블에 쓸 때 명시적으로 값을 제공하지 않거나 사용자가 해당 컬럼에 대해 명시적으로 `DEFAULT` SQL 키워드를 지정할 때 컬럼의 기본값을 생성합니다.

쓰기 및 읽기 작업의 의미:
- 이 메타데이터는 읽기 작업이 아닌 쓰기 작업에만 적용됩니다.
- 테이블 쓰기 작업(SQL INSERT, UPDATE, MERGE 명령 등)은 기본값을 사용합니다. 예를 들어, 다음 SQL 명령은 기본값을 사용합니다: `INSERT INTO t VALUES (42, DEFAULT);`
- 새 컬럼을 추가하는 테이블 작업(SQL ALTER TABLE ... ADD COLUMN 명령 등)은 컬럼이 생성되는 동일한 명령에서 컬럼에 대한 기본값을 지정해서는 안 됩니다. 예를 들어, 다음 SQL 명령은 Delta Lake에서 지원되지 않습니다: `ALTER TABLE t ADD COLUMN c INT DEFAULT 42;`
- 그러나 이전 명령에서 이미 생성된 컬럼에 대한 기본값을 할당하거나 업데이트하는 것은 허용됩니다. 예를 들어, 다음 SQL 명령은 유효합니다: `ALTER TABLE t ALTER COLUMN c SET DEFAULT 42;`

활성화:
- 테이블은 Writer 버전 7에 있어야 하며, 테이블 `protocol`의 `writerFeatures`에 기능 이름 `allowColumnDefaults`가 존재해야 합니다.

활성화된 경우:
- 테이블 스키마의 컬럼에 대한 `metadata`는 키 `CURRENT_DEFAULT`를 포함할 수 있습니다.
- `CURRENT_DEFAULT`의 값은 SQL 표현식으로 구문 분석되어야 합니다.
- Writer는 테이블에 행을 쓰기 전에 기본값이 있는 컬럼에 대한 명시적 값(NULL 포함)이 없는 요청된 각 행에 대해 쓰기 시스템이 각 해당 컬럼에 대한 기본값 표현식을 평가한 결과를 행의 해당 컬럼 값으로 할당하도록 강제해야 합니다. 마찬가지로 엔진이 컬럼에 대해 명시적인 `DEFAULT` SQL 키워드를 지정한 경우 표현식 결과를 같은 방식으로 대체해야 합니다.
- `variant` 타입의 모든 컬럼은 기본적으로 null이어야 합니다.

## Identity 컬럼

Delta는 Delta 테이블에 Identity 컬럼 정의를 지원합니다. Delta는 사용자가 테이블에 쓸 때 명시적으로 값을 제공하지 않을 때 Identity 컬럼에 대한 고유 값을 생성합니다. Identity 컬럼을 지원하려면:
- 테이블은 Writer 버전 6에 있거나
- 테이블은 Writer 버전 7에 있어야 하며, 테이블 `protocol`의 `writerFeatures`에 기능 이름 `identityColumns`가 존재해야 합니다.

지원되는 경우, 테이블 스키마의 컬럼에 대한 `metadata`는 Identity 컬럼 속성에 대해 다음 키를 포함할 수 있습니다:
- `delta.identity.start`: Identity 컬럼의 시작 값입니다. long 타입 값입니다. 테이블 생성 후에는 변경해서는 안 됩니다.
- `delta.identity.step`: 다음 Identity 값으로의 증분입니다. long 타입 값입니다. 0으로 설정할 수 없습니다. 테이블 생성 후에는 변경해서는 안 됩니다.
- `delta.identity.highWaterMark`: Identity 컬럼에 대해 생성된 최고 값입니다. long 타입 값입니다. `delta.identity.step`이 양수(음수)인 경우, 이는 컬럼의 가장 큰(가장 작은) 값이어야 합니다.
- `delta.identity.allowExplicitInsert`: 이 컬럼이 명시적으로 삽입된 값을 허용하는 경우 true입니다. boolean 타입 값입니다. 테이블 생성 후에는 변경해서는 안 됩니다.

`delta.identity.allowExplicitInsert`가 true인 경우, writer는 다음 요구사항을 충족해야 합니다:
- 사용자는 Identity 컬럼에 대해 자체 값을 제공할 수 있어야 합니다.

`delta.identity.allowExplicitInsert`가 false인 경우, writer는 다음 요구사항을 충족해야 합니다:
- 사용자는 Identity 컬럼에 대해 자체 값을 제공할 수 없어야 합니다.
- Delta는 다음 요구사항을 만족하는 값을 생성해야 합니다
    - 새 값은 컬럼에 이미 존재하지 않아야 합니다.
    - 새 값은 `value = start + k * step`을 만족해야 하며, 여기서 k는 음이 아닌 정수입니다.
    - 새 값은 `delta.identity.highWaterMark`보다 높아야 합니다. `delta.identity.step`이 양수(음수)인 경우, 새 값은 `delta.identity.highWaterMark`보다 커야(작아야) 합니다.
- 생성된 Identity 값을 계산할 때의 오버플로는 감지되어야 하며 그러한 쓰기는 허용되지 않아야 합니다.
- `delta.identity.highWaterMark`는 쓰기 작업이 커밋될 때 새로운 최고 값으로 업데이트되어야 합니다.

## 삭제 벡터 형식

삭제 벡터는 기본적으로 행 인덱스 집합으로, 0부터 시작하는 parquet 파일의 행 위치(인덱스)를 설명하는 64비트 정수입니다. 우리는 이러한 집합을 압축된 형식으로 저장합니다. 이를 위한 기본 구성 요소는 오픈 소스 [RoaringBitmap](https://roaringbitmap.org/) 라이브러리입니다. RoaringBitmap은 16비트 블록(64K 값)의 세분성에서 세 가지 다른 인코딩 간에 자동으로 전환하는 32비트 정수 저장을 위한 유연한 형식입니다:

- 블록의 값 수가 적을 때 간단한 정수 배열.
- 블록의 값 수가 많고 분산되어 있을 때 비트맵 압축.
- 블록의 값 수가 많지만 클러스터화되어 있을 때 Run-length 인코딩.

직렬화 형식은 [표준화](https://github.com/RoaringBitmap/RoaringFormatSpec)되어 있으며, [Java](https://github.com/lemire/RoaringBitmap/) 및 [C/C++](https://github.com/RoaringBitmap/CRoaring) 구현을 사용할 수 있습니다(다른 것들도 있음).

위 설명은 32비트 비트맵에만 적용되지만 삭제 벡터는 64비트 정수를 사용합니다. 32비트에서 64비트로 범위를 확장하기 위해 RoaringBitmaps는 [RoaringBitmaps 사양](https://github.com/RoaringBitmap/RoaringFormatSpec#extention-for-64-bit-implementations)에서 "portable" 직렬화 형식을 정의합니다. 이 형식은 기본적으로 공간을 외부 부분으로 분할하며, 가장 중요한 32비트 "키"가 오름차순 시퀀스에서 가장 덜 중요한 32비트 RoaringBitmaps를 인덱싱합니다. 사양은 이러한 가장 덜 중요한 32비트 RoaringBitmaps를 "버킷"이라고 부릅니다.

바이트 | 이름 | 설명
-|-|-
0 – 7 | numBuckets | 이 비트맵의 고유한 32비트 버킷 수.
`각 버킷 b에 대해 반복` | | 키의 오름차순으로 각 버킷에 대해.
`<b의 시작>` – `<b의 시작> + 3` | key | 이 버킷의 모든 값의 가장 중요한 32비트.
`<b의 시작> + 4` – `<b의 끝>` | bucketData | 이 버킷의 모든 가장 덜 중요한 32비트 항목이 있는 직렬화된 32비트 RoaringBitmap.

32비트 직렬화 형식은 모든 (가장 덜 중요한) 16비트 컨테이너, 해당 타입(위 참조) 및 키(가장 중요한 16비트)를 설명하는 헤더로 구성됩니다.
이는 컨테이너별 형식의 각 개별 컨테이너에 대한 데이터가 뒤따릅니다.

Roaring 형식의 참조 구현:

- [32비트 Java RoaringBitmap](https://github.com/RoaringBitmap/RoaringBitmap/blob/c7993318d7224cd3cc0244dcc99c8bbc5ddb0c87/RoaringBitmap/src/main/java/org/roaringbitmap/RoaringArray.java#L905-L949)
- [64비트 Java RoaringNavigableBitmap](https://github.com/RoaringBitmap/RoaringBitmap/blob/c7993318d7224cd3cc0244dcc99c8bbc5ddb0c87/RoaringBitmap/src/main/java/org/roaringbitmap/longlong/Roaring64NavigableMap.java#L1253-L1260)

Delta는 위에서 설명한 형식을 블랙박스로 사용하지만 두 가지 추가 사항이 있습니다:

1. "매직 넘버"를 앞에 추가하여 올바른 형식을 읽고 있는지 확인하고 향후 형식을 발전시킬 수 있는 능력을 유지합니다.
2. 비트맵의 모든 "키"(위 참조)는 가장 중요한 비트가 0이어야 합니다. 이는 Java에서 값을 부호 있는 것으로 읽을 때 음수 키를 읽지 않도록 보장합니다.

구체적인 직렬화 형식은 다음과 같습니다(모든 숫자 값은 little endian 바이트 순서로 작성됨):

바이트 | 이름 | 설명
-|-|-
0 — 3 | magicNumber | 1681511377; 다음 바이트가 정확히 이 형식으로 직렬화되었음을 나타냅니다. 미래의 대체적이지만 관련된 형식은 예를 들어 이를 증가시켜 다른 매직 넘버를 가져야 합니다.
4 — end | bitmap | [RoaringBitmaps 사양](https://github.com/RoaringBitmap/RoaringFormatSpec#extention-for-64-bit-implementations)에 정의된 portable 표준 형식의 직렬화된 64비트 비트맵. 이는 네이티브 표준 준수 RoaringBitmap 라이브러리를 사용할 수 있는 Delta 구현에 의해 블랙박스로 처리될 수 있습니다.

### 삭제 벡터 파일 저장 형식

삭제 벡터는 클라우드 스토리지의 파일 또는 Delta 로그에 인라인으로 저장될 수 있습니다.
파일 스토리지에 DV를 저장하는 형식은 이전 섹션에서 설명한 64비트 RoaringBitmaps를 사용하는 파일당 하나(또는 그 이상)의 DV와 각 DV에 대한 체크섬입니다.
구체적인 형식은 다음과 같으며, 모든 숫자 값은 big endian 바이트 순서로 작성됩니다:

바이트 | 이름 | 설명
-|-|-
0 | version | 이 파일의 형식 버전: 여기서 설명하는 형식의 경우 `1`.
`각 DV i에 대해 반복` | | 각 DV에 대해
`<i의 시작>` — `<i의 시작> + 3` | dataSize | 이 DV의 데이터 크기(체크섬 제외)
`<i의 시작> + 4` — `<i의 시작> + 4 + dataSize - 1` | bitmapData | 위에서 설명한 대로 직렬화된 하나의 64비트 RoaringBitmap.
`<i의 시작> + 4 + dataSize` — `<i의 시작> + 4 + dataSize + 3` | checksum | `bitmapData`의 CRC-32 체크섬

## 파일별 통계
`add` 및 `remove` 액션은 선택적으로 테이블에서 추가되거나 제거되는 파일의 데이터에 대한 통계를 포함할 수 있습니다.
이러한 통계는 쿼리 조건자를 기반으로 파일을 제거하거나 쿼리 최적화의 입력으로 사용할 수 있습니다.

전역 통계는 전체 파일에 대한 정보를 기록합니다.
현재 다음 전역 통계가 지원됩니다:

이름 | 설명
-|-
numRecords | 이 데이터 파일의 레코드 수.
tightBounds | 컬럼별 통계가 현재 **tight** 또는 **wide**인지 여부(아래 참조).

`deletionVector`가 `null`이 아닌 논리적 파일의 경우, `numRecords` 통계는 *반드시* 존재하고 정확해야 합니다. 즉, 논리적 파일의 유효한 레코드가 아닌 데이터 파일의 레코드 수와 같아야 합니다.
[삭제 벡터](#삭제-벡터)가 있는 경우 통계는 다소 오래된 것일 수 있습니다. 즉, 아직 삭제된 행을 반영하지 않습니다. `stats.tightBounds` 플래그는 **tight bounds**(즉, minValue/maxValue가 파일의 유효한 상태에 존재함[^1])인지 또는 **wide bounds**(즉, minValue는 파일의 모든 유효한 값보다 작거나 같고, maxValue는 파일의 모든 유효한 값보다 크거나 같음)인지를 나타냅니다. 이러한 상한/하한은 데이터 건너뛰기에 충분한 정보입니다. 참고로, `stats.tightBounds`는 통계에 명시적으로 존재하지 않을 때 `true`로 처리되어야 합니다.

컬럼별 통계는 파일의 각 컬럼에 대한 정보를 기록하며 실제 데이터의 스키마를 반영하여 인코딩됩니다.
예를 들어, 다음 데이터 스키마가 주어진 경우:
```
|-- a: struct
|    |-- b: struct
|    |    |-- c: long
```

통계는 다음 스키마로 저장될 수 있습니다:
```
|-- stats: struct
|    |-- numRecords: long
|    |-- tightBounds: boolean
|    |-- minValues: struct
|    |    |-- a: struct
|    |    |    |-- b: struct
|    |    |    |    |-- c: long
|    |-- maxValues: struct
|    |    |-- a: struct
|    |    |    |-- b: struct
|    |    |    |    |-- c: long
```

현재 다음 컬럼별 통계가 지원됩니다:

이름 | 설명 (`stats.tightBounds=true`) | 설명 (`stats.tightBounds=false`)
-|-|-
nullCount | 이 컬럼에 대한 `null` 값의 수 | <p>컬럼의 `nullCount`가 물리적 레코드 수(`stats.numRecords`)와 같으면 이 컬럼의 **모든** 유효한 행이 `null` 값을 가져야 합니다(역은 반드시 참이 아님).</p><p>컬럼의 `nullCount`가 0이면 **모든** 유효한 행이 이 컬럼에서 non-`null`입니다(역은 반드시 참이 아님).</p><p>컬럼의 `nullCount`가 이 두 특수 케이스 이외의 값이면 값은 정보를 전달하지 않으며 없는 것처럼 처리되어야 합니다.</p>
minValues | 이 컬럼에 대해 파일에 존재하는 가장 작은 유효한 값[^1]과 같은 값. 모든 유효한 행이 null이면 이는 정보를 전달하지 않습니다. | 이 파일의 이 컬럼에 존재하는 모든 유효한 값[^1]보다 작거나 같은 값. 모든 유효한 행이 null이면 이는 정보를 전달하지 않습니다.
maxValues | 이 컬럼에 대해 파일에 존재하는 가장 큰 유효한 값[^1]과 같은 값. 모든 유효한 행이 null이면 이는 정보를 전달하지 않습니다. | 이 파일의 이 컬럼에 존재하는 모든 유효한 값[^1]보다 크거나 같은 값. 모든 유효한 행이 null이면 이는 정보를 전달하지 않습니다.

[^1]: 문자열 컬럼은 고정 접두사 길이에서 잘립니다. 타임스탬프 컬럼은 밀리초로 잘립니다.

## 파티션 값 직렬화

파티션 값은 다음 형식을 사용하여 문자열로 저장됩니다. 모든 타입에 대한 빈 문자열은 `null` 파티션 값으로 변환됩니다.

타입 | 직렬화 형식
-|-
string | 변환 필요 없음
numeric types | 숫자의 문자열 표현
date | `{year}-{month}-{day}`로 인코딩. 예: `1970-01-01`
timestamp | `{year}-{month}-{day} {hour}:{minute}:{second}` 또는 `{year}-{month}-{day} {hour}:{minute}:{second}.{microsecond}`로 인코딩. 예: `1970-01-01 00:00:00` 또는 `1970-01-01 00:00:00.123456`. 타임스탬프는 `1970-01-01T00:00:00.123456Z`와 같이 UTC 타임스탬프로 조정된 ISO8601 형식 타임스탬프로 인코딩될 수도 있습니다.
timestamp without timezone | `{year}-{month}-{day} {hour}:{minute}:{second}` 또는 `{year}-{month}-{day} {hour}:{minute}:{second}.{microsecond}`로 인코딩. 예: `1970-01-01 00:00:00` 또는 `1970-01-01 00:00:00.123456` 이 타입을 사용하려면 테이블이 `timestampNtz` 기능을 지원해야 합니다. 자세한 내용은 [시간대가 없는 타임스탬프 (TimestampNtz)](#시간대가-없는-타임스탬프-timestampntz) 섹션을 참조하세요.
boolean | "true" 또는 "false" 문자열로 인코딩
binary | 이스케이프된 바이너리 값의 문자열로 인코딩. 예: `"\u0001\u0002\u0003"`

참고: 파티션 값의 타임스탬프 값은 다음 중 하나의 방법으로 저장될 수 있습니다:
1. 시간대 없이, 타임스탬프는 테이블에 쓴 시스템의 시간대를 사용하여 해석되어야 합니다.
2. UTC로 조정되고 ISO8601 형식으로 저장됩니다.

최신 writer는 타임스탬프를 UTC로 조정하고 2에 설명된 대로 ISO8601 형식으로 타임스탬프를 저장하는 것이 권장됩니다.

## 스키마 직렬화 형식

Delta는 Spark SQL의 JSON 스키마 표현의 하위 집합을 사용하여 트랜잭션 로그에 테이블 스키마를 기록합니다.
모든 컬럼 이름은 대소문자에 관계없이 고유해야 합니다.
참조 구현은 [Apache Spark 저장소의 catalyst 패키지](https://github.com/apache/spark/tree/master/sql/catalyst/src/main/scala/org/apache/spark/sql/types)에서 찾을 수 있습니다.

### 기본 타입

타입 이름 | 설명
-|-
string| UTF-8 인코딩 문자열
long| 8바이트 부호 있는 정수. 범위: -9223372036854775808 ~ 9223372036854775807
integer|4바이트 부호 있는 정수. 범위: -2147483648 ~ 2147483647
short| 2바이트 부호 있는 정수. 범위: -32768 ~ 32767
byte| 1바이트 부호 있는 정수. 범위: -128 ~ 127
float| 4바이트 단정밀도 부동소수점 숫자
double| 8바이트 배정밀도 부동소수점 숫자
decimal| 고정 정밀도(최대 자릿수)와 스케일(소수점 오른쪽 자릿수)을 가진 부호 있는 십진수. 정밀도와 스케일은 최대 38까지 가능합니다.
boolean| `true` 또는 `false`
binary| 바이너리 데이터 시퀀스.
date| 시간대 없이 연-월-일 삼중항으로 표현되는 달력 날짜.
timestamp| Unix epoch(1970-01-01 00:00:00 UTC) 이후 경과된 마이크로초 정밀도 타임스탬프. parquet 파일에 저장될 때 `isAdjustedToUTC`는 `true`로 설정되어야 합니다.
timestamp without time zone | Unix epoch(1970-01-01 00:00:00) 이후 경과된 로컬 시간대의 마이크로초 정밀도 타임스탬프. 시간대 정보가 없으며, 이 타입의 값은 여러 물리적 시간 순간에 매핑될 수 있습니다. 현재 로컬 시간대에 관계없이 항상 같은 방식으로 표시되어야 합니다. parquet 파일에 저장될 때 `isAdjustedToUTC`는 `false`로 설정되어야 합니다. 이 타입을 사용하려면 테이블이 `timestampNtz` 기능을 지원해야 합니다. 자세한 내용은 [시간대가 없는 타임스탬프 (TimestampNtz)](#시간대가-없는-타임스탬프-timestampntz) 섹션을 참조하세요.

타임스탬프 및 `isAdjustedToUTC`에 대한 자세한 내용은 Parquet [타임스탬프 타입](https://github.com/apache/parquet-format/blob/master/LogicalTypes.md#timestamp)을 참조하세요.

참고: 기존 테이블에는 `void` 데이터 타입 컬럼이 있을 수 있습니다. `void` 데이터 타입 컬럼에 대한 동작은 정의되지 않았지만 읽기 시 `void` 데이터 타입 컬럼을 삭제하는 것이 권장됩니다(Spark 커넥터에서 구현된 대로).

### Struct 타입

struct는 테이블의 최상위 스키마와 중첩 컬럼을 포함하는 struct 컬럼을 모두 나타내는 데 사용됩니다. struct는 다음 필드가 있는 JSON 객체로 인코딩됩니다:

필드 이름 | 설명
-|-
type | 항상 문자열 "struct"
fields | 필드 배열

### Struct 필드

struct 필드는 최상위 또는 중첩 컬럼을 나타냅니다.

필드 이름 | 설명
-|-
name| 이 (중첩될 수 있는) 컬럼의 이름
type| 기본 타입의 이름, struct 정의, 배열 정의 또는 맵 정의를 포함하는 문자열
nullable| 이 필드가 null일 수 있는지 나타내는 Boolean
metadata| 이 컬럼에 대한 정보를 포함하는 JSON 맵. `Delta` 접두사가 있는 키는 구현을 위해 예약되어 있습니다. 테이블에 쓸 때 클라이언트가 처리해야 하는 컬럼 수준 메타데이터에 대한 자세한 내용은 [컬럼 메타데이터](#column-metadata)를 참조하세요.

### 배열 타입

배열은 어떤 타입의 항목에 대한 가변 길이 컬렉션을 저장합니다.

필드 이름 | 설명
-|-
type| 항상 문자열 "array"
elementType| 이 배열에 저장된 요소의 타입, 기본 타입의 이름, struct 정의, 배열 정의 또는 맵 정의를 포함하는 문자열로 표현됨
containsNull| 이 배열이 하나 이상의 null 값을 포함할 수 있는지 나타내는 Boolean

### 맵 타입

맵은 단일 `keyType`과 단일 `valueType`을 가진 키-값 쌍의 임의 길이 컬렉션을 저장합니다.

필드 이름 | 설명
-|-
type| 항상 문자열 "map".
keyType| 이 맵의 키에 사용되는 요소의 타입, 기본 타입의 이름, struct 정의, 배열 정의 또는 맵 정의를 포함하는 문자열로 표현됨
valueType| 이 맵의 값에 사용되는 요소의 타입, 기본 타입의 이름, struct 정의, 배열 정의 또는 맵 정의를 포함하는 문자열로 표현됨

### Variant 타입

Variant 데이터는 Delta 스키마 직렬화를 위해 Delta 타입 이름 `variant`를 사용합니다.

필드 이름 | 설명
-|-
type | 항상 문자열 "variant"

### 컬럼 메타데이터
컬럼 메타데이터는 컬럼에 대한 다양한 정보를 저장합니다.
예를 들어, [`delta.columnMapping`](#컬럼-매핑) 또는 [`delta.generationExpression`](#생성된-컬럼) 또는 [`CURRENT_DEFAULT`](#기본-컬럼)와 같은 일부 키를 포함할 수 있습니다.  
필드 이름 | 설명
-|-
delta.columnMapping.*| 이러한 키는 논리적 컬럼 이름과 물리적 이름 간의 매핑에 대한 정보를 저장하는 데 사용됩니다. 자세한 내용은 [컬럼 매핑](#컬럼-매핑)을 참조하세요.
delta.identity.*| 이러한 키는 identity 컬럼 정의를 위한 것입니다. 자세한 내용은 [Identity 컬럼](#identity-컬럼)을 참조하세요.
delta.invariants| SQL 표현식 정보를 포함하는 JSON 문자열. 자세한 내용은 [컬럼 불변성](#컬럼-불변성)을 참조하세요.
delta.generationExpression| SQL 표현식 문자열. 자세한 내용은 [생성된 컬럼](#생성된-컬럼)을 참조하세요.
delta.typeChanges| 이 컬럼에 적용된 이전 타입 변경에 대한 정보를 포함하는 JSON 문자열. 자세한 내용은 [Type Change Metadata](#type-change-metadata)를 참조하세요.

## 마지막 체크포인트 파일 스키마

이 마지막 체크포인트 파일은 JSON으로 인코딩되며 다음 정보를 포함합니다:

필드 | 설명
-|-
version | 마지막 체크포인트가 생성되었을 때의 테이블 버전.
size | 체크포인트에 저장된 액션의 수.
parts | 마지막 체크포인트가 여러 파트로 작성된 경우 프래그먼트 수. 이 필드는 선택 사항입니다.
sizeInBytes | 체크포인트의 바이트 수. 이 필드는 선택 사항입니다.
numOfAddFiles | 체크포인트의 AddFile 액션 수. 이 필드는 선택 사항입니다.
checkpointSchema | 체크포인트 파일의 스키마. 이 필드는 선택 사항입니다.
tags | 마지막 체크포인트에 대한 추가 메타데이터를 포함하는 문자열-문자열 맵. 이 필드는 선택 사항입니다.
checksum | 마지막 체크포인트 JSON의 체크섬. 이 필드는 선택 사항입니다.

checksum 필드는 마지막 체크포인트 JSON 파일의 필드에 대한 MD5 체크섬을 포함하는 선택적 필드입니다.
마지막 체크포인트 파일 reader는 존재하는 경우 체크섬을 검증하도록 권장되며, writer는 파일을 덮어쓸 때 체크섬을 작성하도록 권장됩니다. 마지막 체크포인트 JSON의 체크섬 필드 계산 규칙은 [이 섹션](#json-checksum)을 참조하세요.

### JSON 체크섬
마지막 체크포인트 JSON의 체크섬을 생성하려면 먼저 체크섬 JSON을 정규화하고 문자열로 변환합니다. 그런 다음 결과 문자열에서 32자 MD5 다이제스트를 계산하여 체크섬을 얻습니다. [JSON](https://datatracker.ietf.org/doc/html/rfc8259) 정규화 규칙은 다음과 같습니다:

1. 리터럴 값(`true`, `false`, `null`)은 고유한 정규 형식입니다
2. 숫자 값(예: `42` 또는 `3.14`)은 고유한 정규 형식입니다
3. 문자열 값(예: `"hello world"`)은 주변 따옴표를 보존하고 내용을 [URL 인코딩](#how-to-url-encode-keys-and-string-values)하여 정규화됩니다, 예: `"hello%20world"`
4. 객체 값(예: `{"a": 10, "b": {"y": null, "x": "https://delta.io"} }`)은 다음과 같이 정규화됩니다:
    * 타입(리터럴, 숫자, 문자열)에 대한 규칙에 따라 각 스칼라(리프) 값을 정규화합니다
    * 해당 값에 대한 경로를 따라 각 (문자열) 이름을 정규화합니다
    * 경로 세그먼트를 `+`로 연결합니다, 예: `"b"+"y"`
    * 경로와 값 쌍을 `=`로 연결합니다, 예: `"b"+"y"=null`
    * 경로에 대한 바이트 순서 정렬을 사용하여 정규화된 경로/값 쌍을 정렬합니다. 바이트 순서 정렬은 UTF-8 문자 집합을 사용하여 경로를 바이트 배열로 변환한 다음 비교하여 수행할 수 있습니다, 예: `"a" < "b"+"x" < "b"+"y"`
    * 순서가 지정된 쌍을 `,`로 구분합니다, 예: `"a"=10,"b"+"x"="https%3A%2F%2Fdelta.io","b"+"y"=null`

5. 배열 값(예: `[null, "hi ho", 2.71]`)은 객체인 것처럼 정규화되지만 "이름"이 문자열 타입 대신 숫자 타입이며 해당 배열 요소의 (0 기반) 위치를 제공합니다, 예: `0=null,1="hi%20ho",2=2.71`

6. 최상위 `checksum` 키는 정규화 프로세스에서 무시됩니다. 예:
   `{"k1": "v1", "checksum": "<anything>", "k3": 23}`는 `"k1"="v1","k3"=23`로 정규화됩니다

7. 중복 키는 마지막 체크포인트 JSON에서 허용되지 않으며 그러한 JSON은 유효하지 않은 것으로 간주됩니다.

다음 테스트 샘플 JSON이 주어지면 JSON 정규화의 올바른 구현은 해당 정규화된 형식과 체크섬 값을 생성해야 합니다:
예:
Json: `{"k0":"'v 0'", "checksum": "adsaskfljadfkjadfkj", "k1":{"k2": 2, "k3": ["v3", [1, 2], {"k4": "v4", "k5": ["v5", "v6", "v7"]}]}}`\
정규화된 형식: `"k0"="%27v%200%27","k1"+"k2"=2,"k1"+"k3"+0="v3","k1"+"k3"+1+0=1,"k1"+"k3"+1+1=2,"k1"+"k3"+2+"k4"="v4","k1"+"k3"+2+"k5"+0="v5","k1"+"k3"+2+"k5"+1="v6","k1"+"k3"+2+"k5"+2="v7"`\
체크섬은 `6a92d155a59bf2eecbd4b4ec7fd1f875`

#### 키와 문자열 값을 URL 인코딩하는 방법
[URL 인코딩](https://datatracker.ietf.org/doc/html/rfc3986) 사양은 신뢰할 수 있는 인코딩을 제공하기 위해 약간 유연합니다. 예를 들어, 사양은 퍼센트 인코딩의 일부로 대문자와 소문자를 모두 허용합니다. 따라서 인코딩을 위한 더 엄격한 규칙 세트가 필요합니다:

1. 인코딩될 문자열은 UTF-8 문자 인코딩에 따라 옥텟으로 표현되어야 합니다
2. a-z / A-Z / 0-9 / "-" / "." / "_" / "~"를 제외한 모든 옥텟은 예약되어 있습니다
3. 예약된 옥텟은 항상 [퍼센트 인코딩](https://datatracker.ietf.org/doc/html/rfc3986#section-2)합니다
4. 예약되지 않은 옥텟은 절대 퍼센트 인코딩하지 않습니다
5. 퍼센트 인코딩된 옥텟은 세 문자로 구성됩니다: `%` 뒤에 대문자로 된 2자리 16진수 값, 예: `>`는 `%3E`로 인코딩됩니다

## Delta 데이터 타입에서 Parquet 타입으로의 매핑
아래 표는 각 Delta 데이터 타입이 Parquet 파일에 물리적으로 저장되는 방법을 보여줍니다. Parquet 파일은 테이블 데이터 또는 메타데이터([체크포인트](#체크포인트))를 저장하는 데 사용됩니다. Parquet에는 제한된 수의 [물리적 타입](https://parquet.apache.org/docs/file-format/types/)이 있습니다. Parquet [논리적 타입](https://github.com/apache/parquet-format/blob/master/LogicalTypes.md)은 물리적 타입을 해석하는 방법을 지정하여 타입을 확장하는 데 사용됩니다.

일부 Delta 데이터 타입의 경우 Parquet 파일에 값을 물리적으로 저장하는 여러 방법이 있습니다. 예를 들어, `timestamp`는 `int96` 또는 `int64`로 저장될 수 있습니다. 정확한 물리적 타입은 Parquet 파일을 작성하는 엔진 및/또는 엔진별 구성 옵션에 따라 다릅니다. Delta lake 테이블 reader의 경우 Parquet 파일 reader가 아래 표에 언급된 Parquet 물리적 및 논리적 타입을 최소한 지원하는 것이 권장됩니다.
